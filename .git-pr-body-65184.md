## What changed
Rows that might park are skipped everywhere first, before any code that parks:
- reconcile (`reconcileObservedProviderStatus`, `applyObservedProviderStatus`) and its candidate query
- the health cron's live query
- the runtime-limit cron
- resume preflight, so access verbs never probe a parked machine and retire it

Park job (`services/vms/addressReleaseJob.ts`), run from the vm-idle-pause cron. It handles paused Freestyle rows past N hours that have no home volume, are not sandbox runs, and have a recorded shape their plan can restore. A row with no recorded shape claims the provider maximum, which a smaller plan would refuse on restore, so it never parks. For each row:
1. Check that the provider reports the machine `paused`.
2. Take a snapshot and verify it through `listSnapshots`.
3. Record a `vm.snapshot.created` ownership event.
4. Write `addressRelease.state = parking`, fenced on id, provider id, status and `updated_at`.
5. Check pause state again.
6. Destroy the provider machine.
7. Write `parked` and drop `networkIpv4`, which takes the row out of `countNetworkAddressHolders`.

A failure before step 6 destroys nothing. A row left `parking` keeps its address in the count. The next run either finishes it (the machine is already gone) or snapshots again (the machine is still paused).

Resume: `resumeParkedVm` calls `restoreVm(snapshotId)` with the key `park-restore:<row id>` and passes `waitForCapacity` through. It reads the shape the park recorded on every plan, not only paid ones. Admission and `waiting_for_address` are the normal create's. It then retires the parked row with `successorProviderVmId` and revokes the old model-plane token. `requireUserVm` follows the successor pointer one hop, so the old id keeps working. A plain `resumeVm` on a parked row answers unsupported. The main twin wires the route.

## Tests (`web/tests/vm-address-release.test.ts`)
- Flag off: nothing is snapshotted or destroyed.
- Nothing is destroyed when:
  - the provider refuses the snapshot
  - the snapshot is missing from `listSnapshots`
  - the row was changed after it was read
  - the machine woke after the snapshot
  - the machine is not reported paused
- A failed destroy keeps the row `parking` and its address counted; the next run finishes it.
- A run that destroyed the machine but lost the final write is finished on the next run without a second snapshot.
- Home-volume and sandbox-run machines are never touched, and neither is a machine whose plan could not restore its shape.
- Reconcile leaves a parked row alone. A plain resume refuses.
- Receipt: a create at the cap answers `waiting_for_address`, a row parks, and the same-key retry starts. A parked-row resume at the cap waits, restores once another row parks, and the old id follows the successor.

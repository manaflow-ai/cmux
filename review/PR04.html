PR04 — Preserve persistent daemon owner across app updates

Local proposal artifact · Draft for review · No branch, commit, or public PR

Outcome: a version-changing app relaunch reattaches a live persistent PTY through the daemon namespace that owns it. It never silently starts a replacement shell while the old process remains alive.

Discovered defect

  • SessionRemoteWorkspaceSnapshot persists persistentDaemonSlot and terminal session ID but no daemon owner version/path.
  • RemoteSessionCoordinator.remoteDaemonVersion() selects the current app version on restore.
  • The remote server stores slot credentials/socket state under ~/.cmux/daemon/<compiled-version>/<slot>.
  • After app A updates to B, restored --require-existing can connect to B's empty hub, return status 253, and hit the existing CLI fallback remote session was lost; starting a new shell. The A-owned PTY can remain alive but inaccessible.
  • This is separate from the reported initial readiness hang. Sparkle replacement triggers the version transition but is not itself faulty.

Persistence contract

Add a Codable, Equatable, Sendable owner value with exact fields:

public struct PersistentRemoteDaemonOwner: Codable, Equatable, Sendable {
    public var version: String
    public var remotePath: String
}
  • Add optional persistentDaemonOwner: PersistentRemoteDaemonOwner? to WorkspaceRemoteConfiguration and SessionRemoteWorkspaceSnapshot. Optional field keeps old snapshots decodable.
  • Only a successful managed persistent bootstrap/hello may publish the owner. Normalize nonempty version/path; malformed snapshot owner is ignored with the existing backward-compatible current-version behavior only when no persisted PTY session is marked established.
  • When an established persisted session has a valid owner, owner recovery is fail-closed: missing/unusable owner path is a visible recovery error, not proof of session absence and not permission to start a new shell.

Production change contract

  1. After selected daemon bootstrap succeeds and its hello is accepted, publish PersistentRemoteDaemonOwner(version: hello.version, remotePath: hello.remotePath) to the Workspace through the existing coordinator host/state delivery path; snapshot it in persistSessionForUpdateRelaunch.
  2. On app-B restore of an established PTY owned by A, construct the proxy/stdio attach from the persisted A remote path and issue --require-existing. Do not probe/bootstrap B first and do not invoke the 253 new-shell fallback.
  3. Keep the workspace on A while any exact established session mapping owned by A remains. New panes in that persistent workspace use A so one slot is not split across owner namespaces.
  4. Only an exact current confirmed_absent or explicit successful retirement clears the owner. Then bootstrap current B and allow an explicit new shell. A stale/moved/replaced callback cannot cut over.
  5. If A path is missing or hello cannot authenticate, retain owner/session identity and show recovery error. Do not install a B binary at the A path. A separate recovery action may retry A; it may not infer remote absence.
  6. Baked/skip-bootstrap workspaces retain their existing transport contract and do not acquire this managed owner field.

Behavior coverage

  • Start PTY/output under A; snapshot/update/restore under B; prove same session and buffered output reattach through A and zero new-shell fallback calls.
  • Exact confirmed retirement under A clears owner and permits a new B session.
  • Missing A path and failed A hello retain session/owner and emit recovery error; B is not started.
  • Old snapshot without owner follows existing behavior; same-version owner restore works.
  • Deep-sleep, moved surface/Dock, multiple panes in one slot, and stale-generation end retain correct owner.
  • Baked/skip-bootstrap transports remain capability-based and owner-free.

Release-pipeline review

  • Installed GUI and bundled CLI both report 0.64.22 (102) [ddd4a01bc]; no mixed installed executable was observed.
  • Keep final-artifact guards: stable tag equals v<bundle version>, manifest appVersion/releaseTag match final artifact/tag, and all manifest assets/checksums are uploaded.
  • scripts/build-sign-upload.sh does not build/inject a daemon manifest and should be retired or brought to stable-workflow parity before it is considered a supported release path. This is not evidence that it produced the observed install.

Review blockers

  1. Owner is recorded only after accepted hello and persisted before update relaunch.
  2. Established A session never silently falls through to B on 253 or missing path.
  3. Only exact confirmed absence/retirement permits cutover.
  4. Old snapshots and baked transports remain compatible.
  5. Version A → B test proves session identity and buffered output, not merely a connected badge.

Where Feed data comes from, and where it lives

Feed is a view of agent activity recorded by the Mac. The phone fetches and combines that activity from its connected Macs. Notifications are also a Feed input. The Notifications tab keeps its own read and dismissal surface, while Feed projects the same durable notification records alongside agent activity.

Rows can come from notifications too

Hooks, provider plugins, wrapper telemetry, Codex Teams approvals, and the notification history store feed the timeline. A notification creates a Feed row with its notification UUID as the event identity. [1–4]

Mac

Incoming rows are saved on disk

The Mac app keeps a live store and appends incoming items and later mutations to ~/.cmuxterm/workstream.jsonl. Startup collapses repeated JSONL rows to the latest state for each event. [5–7]

Phone

A live mirror backed by Mac state

The phone refetches the authoritative rows after restart. Reply text and the Replied marker come back from the Mac because the reply is stored on the event record; local triage remains device-specific. Sign-in and pairing have their own saved state. [9–10]

The phone communicates with the owning Mac over an authenticated connection. The transport chooses its direct or relay route. Authentication, discovery, and push can involve infrastructure; the inspected Feed path does not use a cloud database as its authoritative row store. “Mac-owned data” does not mean every network connection is infrastructure-free.

Retention and limits

  • Mac startup restores the latest 300 persisted items.
  • Live ingestion caps the working store at 2,000 items. The separate Mac history loader can load older pages.
  • Mobile feed.list returns at most 200 visible items per Mac, fewer if the response-size limit requires it.
  • The phone combines up to 400 rows. There is no mobile older-history cursor here.
  • Full text uses 16 KiB pages with an 8 MiB phone limit.
  • The disk log has no automatic retention limit in this implementation; explicit Feed clear removes it.

Storage ownership and privacy

The default log path is scoped to the local OS user. It is not separated by app tag or Stack account, so development instances can restore history from the same file.

The persistence redactor covers tool/permission payloads. It does not generally redact stop response text or conversational context. Treat the retained content as potentially sensitive local data.

These are code findings, not a completed privacy or crash-recovery audit. Retention, account switching, deletion, and shared-file behavior need explicit release decisions. [5–7]

Decisions before shipping

The implemented design is a useful live activity surface. A durable, cross-device conversation history would require additional work. The items below are findings and proposed acceptance criteria, not silently added implementation scope.

Decision / gapCurrent evidenceProposed acceptance criterion
Durable decisions and repliesIncoming items, resolution mutations, expiry, and terminal reply markers persist on the Mac event record. [6, 9–10]Restart both apps after a reply/approval. The row must preserve the correct result and cannot offer a duplicate action. Choose the authoritative persisted record.
Reliable delivery and deduplicationBest-effort telemetry can be lost. Stop deduplication uses a two-second match on device, workstream, provider, and reason, without the instance tag. [2, 10]Define stable provider event/turn IDs, retry guarantees, and acknowledgement. Repeated delivery produces one row; distinct rapid turns and sibling tags stay distinct.
Meaning of Repliedsubmitted: true confirms terminal submission. It is not a provider/model acknowledgement. [10]Either label this as submitted, or add evidence that the targeted agent accepted a new turn. Verify with each supported provider.
Failure recoveryThe composer closes on Send; failures in the current terminal reply path are logged without a visible retry flow. [14]Preserve the draft and explain failed delivery. A retry after partial paste must not type the reply twice.
History and ownershipNo phone disk cache or mobile history paging. Mac log is unbounded and shares its OS-user path. [5–10]Choose offline reading expectations, retention, cleanup, account/tag separation, and how old unavailable sessions are presented.
Transport compatibilityFull-text feature uses the existing feed.v1 capability; an older capable Mac can lack feed.text. [12]Version or negotiate the new read method, or require coordinated app updates. Older hosts currently produce a read failure rather than full text.
Release integration and verificationFull-text checks pass; newer main has conflicts and broader inherited checks are not green.Reconcile main, run the required checks, and verify real phone replies, deduplication, failure feedback, and restart recovery before merge/release.

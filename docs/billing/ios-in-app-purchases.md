# iOS in-app purchases

The iOS apps sell cmux personal plans through StoreKit 2. RevenueCat is not used. The web server is the source of truth: it verifies every Apple transaction, records every App Store Server Notification, applies the plan entitlement, and feeds analytics.

## Products

Personal plans only. Team stays web-only (per-seat, invoiced to a team). One price book for the web and the App Store (cmuxterm-hq RFD 0037a). The cmux-next apps (`com.cmux.app`, `dev.cmux.app.internal`) sell the cmux NEXT plans; each product grants exactly its own NEXT plan:

| --- | --- | --- | --- | --- | --- | --- |
| Plus | `next_plus` | $20/mo | $29.99/mo | $20.99 | $25.49 | 30,000 machine-minutes, 1 Chief |
| Pro | `next_pro` | $50/mo | $74.99/mo | $52.49 | $63.74 | 75,000 machine-minutes, 2 Chiefs |
| Max | `next_max` | $200/mo | $299.99/mo | $209.99 | $254.99 | 300,000 machine-minutes, 5 Chiefs |
| Team | `team` | $60/seat/mo | web only | - | - | $25 pool a seat |

The classic beta (`dev.cmux.app.beta`) sells the classic plans, which grant classic entitlements:

| Plan | Plan ID | Web (Stripe) | iOS (App Store, USD base) | Net at 30% | Net at 15% |
| --- | --- | --- | --- | --- | --- |
| Go | `go` | $15/mo | $21.99/mo | $15.39 | $18.69 |
| Pro | `pro` | $50/mo | $74.99/mo | $52.49 | $63.74 |
| Max | `max` | $200/mo | $299.99/mo | $209.99 | $254.99 |

The iOS price is the web price divided by 0.7 (Apple's first-year commission), rounded up to the next `.99` price point with a few dollars of margin. This matches what YouTube Premium, Spotify (historically), Tinder, and Bumble do: iOS buyers pay more so net revenue per plan is never below web. After a subscriber's first year, or under the Small Business Program, Apple takes 15% and the margin grows. Other storefronts use Apple's automatic equalization from the US base price.

All products are auto-renewable, in one subscription group per app so upgrades and downgrades are Apple-managed (Max > Pro > Plus, or Max > Pro > Go, level 1 highest). NEXT plans are monthly only, as on the web. No introductory offers or free trials.

Product IDs are prefixed with the bundle ID, so the App Store app and each TestFlight app own their products:

- cmux-next apps: `<bundleId>.next_plus.monthly`, `<bundleId>.next_pro.monthly`, `<bundleId>.next_max.monthly`. The server never maps `go` to `next_plus`.
- Classic app: `<bundleId>.go.monthly`, `<bundleId>.pro.monthly`, `<bundleId>.max.monthly`. These IDs still map to their classic plans in every bundle, so a subscriber renewing one of the old `com.cmux.app` products keeps it; the account-token route no longer lists them to the cmux-next apps.
- Yearly, like the web prices (Pro $480/yr, Max $1,920/yr; Go is monthly only): `<bundleId>.pro.yearly`, `<bundleId>.max.yearly`. The account-token route lists them only to an app that sends `x-cmux-billing-periods: monthly,yearly`; every product entry carries `billingPeriod` (`monthly` | `yearly`). Older apps get monthly products only. Transactions and notifications map either ID to its plan; the grant runs until `expires_at`. Until the App Store yearly prices are set, a non-USD yearly charge is estimated at the monthly list price x 9.6.
- App Store app: bundle `com.cmux.app` (Apple ID 6783338052), the App Store home of cmux-next. Beta: `dev.cmux.app.beta`. cmux INTERNAL, the cmux-next TestFlight build: `dev.cmux.app.internal` (Apple ID 6791408425); its products resolve once they exist in App Store Connect, and production answers it `purchases_unavailable` because it buys only in the Sandbox. Dev builds use a local StoreKit configuration file.

Go is listed only when the server reports it enabled (the Go PostHog flag), same as web.

A NEXT product's grant is mirrored in `cmuxNextPlan` (and `cmuxPlan` while no classic plan holds it), combined with a Stripe NEXT subscription, the higher plan winning; a classic product's grant goes to `cmuxPlan` as before. The two families are picked separately, so a NEXT subscription never counts as a classic plan or the reverse.

## Account linking

Every purchase carries `appAccountToken`, a UUID the server mints once per cmux user and stores (`apple_account_tokens`). The app-posted route rejects a transaction whose token maps to a different user than the caller, or that the server never minted, so one account cannot replay another's transaction. This links Apple subscriptions to cmux accounts without trusting the client. A transaction without a token (an offer code redeemed outside the app) may be claimed by the signed-in user only while no other account owns its original transaction.

The token on the newest transaction decides the owner. When the same Apple ID signs into another cmux account and buys again (an upgrade or a resubscribe), the new transaction carries that account's token, and Apple keeps one original transaction ID for the subscription group. A transaction newer than the stored one (a different transaction ID with a later purchase date) whose token maps to a known cmux user other than the row's owner moves the row to that user and updates `app_account_token`, through either the app-posted route or a notification. Both users' plans are then re-derived; the previous owner falls back to Stripe or free. A token-less transaction, an unknown token, or an older transaction never moves a subscription, and an app post that would leave the row owned by someone else gets 403 `account_mismatch`. If re-deriving the previous owner fails, the stale `cmuxPlan` mirror is corrected by the next read-time reconciliation.

## Server API (web/app/api/billing/apple)

All authenticated routes use the same Stack auth as the other `/api/billing/*` routes (cookie or native bearer + refresh token headers).

- `POST /api/billing/apple/account-token` (auth). Response: `{ appAccountToken, eligible, reason, currentPlan: { planId, source: "stripe" | "apple" | "none", manageUrl? }, products: [{ productId, planId }] }`. `eligible` is false when the user already has an active Stripe subscription, is billed through a team, or this build's purchases would grant no plan; `reason` is a stable code (`stripe_subscription_active`, `team_billing`, `purchases_unavailable`, in that precedence) the app localizes. `products` lists only plans currently sold (Go hidden when its flag is off), for the bundle ID in the `x-cmux-bundle-id` header, and is empty for `purchases_unavailable`. The app sends `x-cmux-storekit-environment` (`Sandbox` or `Production`, read from the signed `AppTransaction`); the server applies the Sandbox entitlement policy (see Entitlement) to that bundle and environment and answers `purchases_unavailable` when a purchase would grant nothing, so a TestFlight build against production never shows a completed purchase with no plan. Without the header, the App Store bundle is assumed Production and every other bundle Sandbox (TestFlight builds always buy in the Sandbox).
- `POST /api/billing/apple/transactions` (auth). Body: `{ signedTransactionInfo: string }` (the StoreKit 2 `jwsRepresentation`). Verifies the JWS chain against Apple's root CA, checks bundle ID, environment, and `appAccountToken` ownership, fetches the current subscription status from the App Store Server API, upserts, applies the entitlement. Response: `{ planId, status, expiresAt }`. Idempotent. Errors: 400 `invalid_transaction` (bad signature, unknown bundle, Xcode/LocalTesting environment), `not_subscription`, `unknown_product`; 403 `account_mismatch`; 409 `family_shared` (a Family Sharing copy of someone else's purchase; see Family Sharing); 503 `verification_unavailable` when Apple's OCSP check is unreachable. Without an App Store Server API key, or when Apple is unreachable or has no status for it, the verified client transaction is used as is, and every such fallback logs `apple_iap.client_transaction_fallback` with a `reason` (`server_api_not_configured`, `unsigned_environment`, `no_status`, `transaction_mismatch`, `lookup_failed`, `production_api_locked_until_release`) for a log metric. The last is expected before the first App Store release (see Production API before the first release) and should be left out of an alert.

  The app finishes a transaction only after a 2xx. Transport errors, 5xx, and 401 (signed out) are retried at launch, sign-in, foreground, and on the plans screen. 400, 403, 404, 409, and 422 are permanent: the purchase shows a terminal error (403 `account_mismatch` says the subscription belongs to another cmux account and to sign in with it), and the app stops re-posting that transaction automatically until the account changes. It never finishes it, so signing in to the owning account still delivers it. Restore Purchases posts it again because the user asked.
- `POST /api/billing/apple/notifications` (public, called by Apple). Body: `{ signedPayload }` (App Store Server Notifications V2). Verifies the envelope and its nested transaction and renewal JWS, writes the ledger row first (idempotent on `notificationUUID`), then upserts subscription state and applies the entitlement. A notification about an older transaction than the row's latest (`REFUND`, `REFUND_DECLINED`, or `REFUND_REVERSED` for a past period) records only its `apple_transactions` row, with the revocation; the subscription row keeps the current period. With an App Store Server API key, the server instead fetches Apple's current status for the subscription and writes that. A refund of the current transaction revokes the subscription. Returns 200 once the ledger row is durable, even if entitlement application fails (a retry job re-applies). Returns 4xx only for payloads that fail verification, and 503 when the ledger write itself failed so Apple redelivers.
- `GET /api/cron/apple-notifications` (Vercel cron, `CRON_SECRET`, at :17 and :47, `maxDuration` 300 s). Four steps, each run even when an earlier one failed; the three that keep paying users' access run first:
  1. **Retry** ledger rows whose `processed_at` is null and that are due: each failed application increments `attempt_count` and sets `next_attempt_at` 5 minutes out, doubling up to 12 hours; after 12 failed attempts (about 3 days) the row is dead-lettered (`dead_lettered_at`), the retry job stops, and `apple_iap.notification_dead_lettered` is logged and reported to error tracking. An Apple redelivery to the webhook still re-applies a dead-lettered row; to requeue one by hand, clear `dead_lettered_at`, `next_attempt_at`, and `attempt_count`. Due rows are taken earliest first, 100 per run, so failing rows never starve newer ones.
  2. **Renewal re-check**: for `active` and `grace_period` rows whose access end is within the next 6 hours or the last hour (auto-renew off included, because the `DID_CHANGE_RENEWAL_STATUS` that turned it back on may be the notification that was missed), and that Apple has not answered for in 25 minutes, the server asks the App Store Server API (`getAllSubscriptionStatuses`) for the current state and verifies it like any signed payload. When that state keeps access (a renewal, a grace period, a plan change at renewal) and differs from the row, it is written through the same forward-only, advisory-locked upsert (`state_signed_at` ordering) and the plan is re-derived; when it matches the row (not renewed yet), only `apple_checked_at` moves. A renewal whose `DID_RENEW` was missed therefore moves `expires_at` forward before the old one passes. The re-check never writes state that removes access; refunds, revocations, and expiry stay with notifications (and the backfill) and the lapse sweep, which retry durably. At most 100 rows per run, soonest end first (`apple_iap.renewal_check_saturated` is logged when more were due). Plan reads never call Apple: they stay one database query, and the re-check runs only in the cron.
  3. **Lapse sweep**: rows still `active`, `grace_period`, or `billing_retry` whose access end, `greatest(expires_at, grace_period_expires_at)`, is more than one hour past and later than the row's `updated_at` (no write or sweep since the lapse), oldest lapse first, 200 per run. With the Server API configured, Apple is asked first (unless it already answered after the lapse in the last 25 minutes): a state that still grants is written and the row is kept (`lapsesRecovered`); Apple agreeing (expired, billing retry without grace, revoked) or having no status lets the sweep expire it. When Apple cannot be asked (an error, or the run's budget is spent), the user is deferred to the next run, for at most 24 hours past the access end, after which the row expires on Apple's last signed state. Without the Server API key the row expires on Apple's last signed state, as before. For each user the sweep re-derives the plan, then marks that user's rows swept: `active` becomes `expired`, `grace_period` becomes `billing_retry` (Apple may still recover it), and `updated_at` moves to the sweep time, so a row matches once per lapse. A failed re-derive leaves the rows unmarked for the next run.
  4. **Backfill** lost notifications through the App Store Server API's Get Notification History, for Production of every accepted bundle and Sandbox of every bundle whose Sandbox purchases can grant here (in production only `com.cmux.app`; see Entitlement). A notification not yet in the ledger goes through the webhook's own path (verify, ledger row idempotent on `notificationUUID`, apply); one already in the ledger is left to the retry job and its backoff. A payload that fails verification is counted as rejected and skipped. A retryable failure (Apple's certificate check unreachable) instead stops that history so the page is read again next run (`apple_iap.history_backfill_stalled`, counted in `retryable_runs`); after 48 such runs in a row (about a day) the still-unverifiable payloads on that page are counted as rejected and logged with their `notificationUUID`, but only when another payload on the same page verified, so one bad payload cannot stall the history while a page where nothing verifies (an outage) keeps stalling. A window runs from the cursor (`apple_notification_history_cursors`, per bundle and environment) minus a one-hour overlap, and spans at most one day, ending no later than now. The first run starts 178 days back (Apple keeps 180), so everything Apple still keeps is covered once; the catch-up moves window by window, each one finishing and moving the cursor long before its start ages out of Apple's 180 days, and a run that finishes a window starts the next one. Up to 5 pages of 20 per history per run, and no page is requested after 200 s of the run; a partly read window saves its pagination token and continues next run, and the cursor moves only after a page is fully ingested. A token Apple rejects (or a start Apple calls too far in the past) restarts the window.

  The re-check and the sweep share 150 status lookups per run. The response reports every count (`notifications`, `deadLettered`, `renewalsChecked`, `renewalsExtended`, `renewalCheckFailures`, `lapsedUsers`, `lapsedFailures`, `lapsedDeferred`, `lapsesRecovered`, `carriesEnded`, `history`, `serverApi`, `productionApi`). It answers 503 when a retry or lapse re-derive failed, a history read failed, both App Store environments refused the key, or a production deployment (`VERCEL_ENV=production`) has no App Store Server API key; the last also logs `apple_iap.server_api_not_configured` with the missing env names and reports to error tracking. Other deployments without the key only warn. The key's presence is also checkable without the cron: every server start logs `apple_iap.server_api_not_configured` (`source: "startup"`, an error in production) when it is missing, and the admin `GET /api/admin/subscriptions/analytics` response carries `billingHealth: { appleServerApi: "configured" | "missing", required, missingEnv }`.

### Production API before the first App Store release

Apple's Production App Store Server API host (`api.storekit.itunes.apple.com`) answers a bodyless HTTP 401 to every call until the app has a production release, even with a key the Sandbox host accepts (Apple developer forums threads 742923, 807236 and 796073: "If your app does not have a production release, you will receive 401 from production endpoints"). For `com.cmux.app` this holds until 1.0.0 is released, and it holds permanently for the TestFlight-only bundles (`dev.cmux.app.beta`, `dev.cmux.app.internal`). It is not a key problem.

The server tells the two cases apart with one Sandbox probe per bundle per cron run, or per request on the client and notification paths (`services/billing/apple/productionAccess.ts`): after a Production 401 it reads the last hour of that bundle's Sandbox notification history with the same key.

- **`locked_until_release`**: Production 401, the Sandbox answers. Quiet: `apple_iap.production_api_locked_until_release` is logged at info, nothing goes to error tracking, and the cron stays 200. The backfill skips that bundle's Production history and leaves its cursor alone (`history.sources[].locked: true`, not a failure), so it starts where it was once Production answers. A client-posted Production transaction (or an older-transaction notification) uses its own verified payload (`reason: production_api_locked_until_release`), as without the Server API. None of these paths ever grants from the locked state. The renewal re-check and the lapse sweep act only on stored Production subscriptions, which cannot exist before a release, so for them the lock is a contradiction: it is logged as `apple_iap.production_api_locked_with_subscription` (an error), the bundle is recorded `unauthorized` for the run (the cron answers 503 and the backfill fails loudly), the re-check counts a failure without writing, and the sweep defers the lapse like an outage, for at most 24 hours. A Production 401 after Production already answered in the same run is never taken for the lock, and a failed Sandbox probe leaves the 401 an ordinary failure (`apple_iap.production_api_probe_failed`, probed once per bundle per run).
- **`unauthorized`**: the Sandbox refuses the key too. A credential error, loud: `apple_iap.server_api_unauthorized` is logged as an error, the backfill fails, the cron answers 503 and reports "App Store Server API refused the key in Production and Sandbox" to error tracking, and the lapse sweep keeps its outage behavior (defer up to 24 hours).
- **`ok`**: Production answered.

The cron response carries `productionApi: { <bundleId>: "ok" | "locked_until_release" | "unauthorized" }` for every bundle it asked Production about. The admin `GET /api/admin/subscriptions/analytics` adds `billingHealth.appleServerApiProduction` for `com.cmux.app`, probed live (the report waits at most 3 s for it) and cached for 5 minutes: `ok`, `locked_until_release`, `unauthorized`, `not_configured` (no key) or `unknown` (Apple could not be asked).

`GET /api/billing/plan` adds `billingSource` (`stripe` | `apple` | `none`) and `manageUrl` (`https://apps.apple.com/account/subscriptions` for Apple). For an App Store subscriber with no recoverable Stripe subscription, `billingManagement` is `external`, a value every installed client already decodes. Personal Stripe checkout redirects an App Store subscriber to `/dashboard/billing`, and the pricing and billing pages show "Manage in the App Store" instead of Stripe checkout.

The same handler serves Production and Sandbox payloads; the `environment` field selects the App Store Server API host.

## Account deletion

Deleting a cmux account does not cancel an App Store subscription; Apple keeps charging until the subscriber cancels it in the App Store (App Store Review Guideline 5.1.1(v)). Before deleting, the iOS app and the dashboard ask `GET /api/account/deletion-check` (auth like the other billing routes; the dashboard reads the same answer through the `settings.accountDeletion` procedure). Response: `{ appStoreSubscriptionRenews, manageSubscriptionsUrl }`. `appStoreSubscriptionRenews` is true when any of the account's `apple_subscriptions` rows is `active`, `grace_period`, or `billing_retry` with `auto_renew_enabled`, in `Production` or `Sandbox` (App Review subscribes in the Sandbox). `manageSubscriptionsUrl` is `https://apps.apple.com/account/subscriptions` then, else null. The app shows a native alert with Manage Subscription (`AppStore.showManageSubscriptions(in:)`, falling back to that URL), Delete Account, and Cancel; the dashboard's delete dialog shows the same warning with a link. The check never blocks deletion. Both delete through `DELETE /api/account` (the dashboard sends the session's bearer and refresh tokens), so every deletion runs the cmux cleanup below.

`DELETE /api/account` then drops the account's link to Apple, in the same transaction as the other cmux rows: the `apple_account_tokens` row and the account's `apple_subscriptions` rows are deleted, and its `apple_transactions` rows are kept as the revenue ledger with `user_id` set to `deleted-account`. A later notification for that subscription finds no row and no token owner and is closed as `skipped: unlinked_account`, so it never grants a plan to the deleted account and the lapse sweep never re-derives one. Renewals after deletion are therefore not recorded in `apple_transactions`. Once the subscription lapses (or on an in-group upgrade), a purchase by the same Apple ID while signed in to another cmux account carries that account's token and creates a new row for it; while the old subscription still renews, its transactions carry the deleted account's token, so Restore Purchases from another account is refused as `account_mismatch`, as it was before.

## Family Sharing

Only the purchaser gets the plan, never their family members. Family Sharing must stay **off** on every subscription in App Store Connect: once it is turned on for a product, Apple does not let it be turned off again. The server enforces the rule anyway, as defense in depth. A transaction whose verified `inAppOwnershipType` is `FAMILY_SHARED` never grants, claims, or changes an `apple_subscriptions` row on any path:

- `POST /api/billing/apple/transactions` records it in `apple_transactions` for audit (attributed to the posting account, after the usual token check) and answers 409 `family_shared`; it does the same when Apple's current status for the subscription is family-shared, which the app treats as permanent.
- A notification about it (`SUBSCRIBED`, `DID_RENEW`, `REVOKE`, anything) is closed as `skipped: family_shared` and records the transaction only when its token maps to a cmux account. A `REVOKE` of a family member's access therefore never revokes the purchaser. The history backfill goes through the same path.
- The renewal re-check and lapse sweep treat an Apple status whose transaction is family-shared as no usable status, so it never extends a row.
- Subscription analytics leave family-shared transactions out of revenue.

Each refusal logs `apple_iap.family_shared_refused`. `PURCHASED` transactions behave as before.

## Data (Drizzle, Postgres)

- `apple_account_tokens`: `user_id` (pk), `app_account_token` (uuid, unique), `created_at`.
- `apple_subscriptions`: `original_transaction_id` (pk), `user_id`, `app_account_token`, `bundle_id`, `environment`, `product_id`, `plan_id`, `status` (`active` | `grace_period` | `billing_retry` | `expired` | `revoked`), `auto_renew_enabled`, `auto_renew_product_id`, `purchase_date`, `original_purchase_date`, `expires_at`, `storefront`, `currency`, `price_milliunits`, `last_transaction_id`, `revoked_at`, `revocation_reason`, `grace_period_expires_at` (from renewal info; billing retry grants only before it), `state_signed_at` (Apple `signedDate` of the data the row was built from; an older payload never overwrites the row), `apple_checked_at` (when the cron last got an App Store Server API answer for it; not a state write, so it never moves `updated_at`), `carried_plan_id`, `carried_until`, `carried_transaction_id` (a paid higher plan kept after an early renewal into a lower one; see Entitlement), `created_at`, `updated_at` (last write or lapse sweep). The row always describes the latest transaction for its original transaction ID: a payload about an older transaction (earlier purchase date, different `last_transaction_id`) never overwrites it, even when it was signed later. Apple's current status from the Server API is the exception: it names the current transaction, so it is written regardless of purchase date. `user_id` follows the newest transaction's token (see Account linking).
- `apple_transactions`: `transaction_id` (pk), `original_transaction_id`, `user_id`, `product_id`, `plan_id`, `environment`, `type`, `purchase_date`, `expires_at`, `price_milliunits`, `currency`, `storefront`, `offer_type`, `revoked_at`, `payload` (jsonb, decoded), `created_at`. One row per renewal, refund, and upgrade, which is what revenue analytics read. `type` is Apple's `transactionReason` (`PURCHASE` or `RENEWAL`); a refund sets `revoked_at` on the refunded transaction.
- `apple_notifications`: `notification_uuid` (pk), `notification_type`, `subtype`, `environment`, `original_transaction_id`, `signed_date`, `payload` (jsonb, decoded, nested JWS replaced by their verified decoded values), `received_at`, `processed_at`, `error`, `attempt_count`, `next_attempt_at`, `dead_lettered_at`. A failed application keeps `processed_at` null, sets `error`, counts the attempt, and schedules the next one (see the cron). A notification that can never apply (no linked cmux account, an unknown product, a Family Sharing transaction, `TEST`, `CONSUMPTION_REQUEST`) is closed with `processed_at` and `error` = `skipped: <reason>`.

- `apple_notification_history_cursors`: `bundle_id`, `environment` (primary key together), `next_start_at` (where the next backfill window starts, before the overlap), `window_start_at`, `window_end_at`, `pagination_token` (set while a window is partly read), `retryable_runs` (consecutive runs stopped by a retryable verification failure on the current page), `updated_at`.

Migrations: `web/db/migrations/20261002120000_apple_in_app_purchases`, `web/db/migrations/20261113120000_apple_iap_recheck_backfill`.

## Entitlement

An Apple subscription in `active`, `grace_period`, or `billing_retry` (Apple keeps access during retry only inside the grace period; follow `gracePeriodExpiresDate`) grants its plan through the same entitlement path Stripe fulfillment uses, with the source recorded as `apple`. When both sources exist, the higher plan wins, and Stripe reconciliation must not remove an Apple-granted plan (and vice versa). Expiry, refund, and revocation remove the Apple grant.

Mechanism: the `cmuxPlan` mirror in Stack `clientReadOnlyMetadata` is the single entitlement. Every write of it (`syncProPlanMetadata` in Stripe fulfillment, read-time reconciliation, and the Apple flows) computes the highest of the active Stripe plan and the granting Apple plan, so neither source can clear or downgrade the other. Grants are time-checked on read (`expires_at`, `grace_period_expires_at`), so a missed notification cannot extend access. A missed renewal cannot end it either: the cron's renewal re-check asks Apple before `expires_at` passes, and the lapse sweep asks Apple before expiring a row (see the cron). An operator `cmuxVmPlan` override still wins and is never rewritten.

Plan changes around an early renewal. Apple charges a renewal up to a day before the period ends and dates the renewal transaction from the next period's start. Two rules follow:
- A state read from Apple's current status (the App Store Server API, used by the app-posted route, the re-check, and a notification about an older transaction) names the current transaction outright. It is written even when its `purchase_date` is earlier than the stored one's, which is the case for an upgrade bought after Apple already charged the next period. Without the Server API key, such an upgrade waits for its own renewal.
- When the early renewal is into a lower plan (a downgrade), the row keeps the paid higher plan in `carried_plan_id` until `carried_until` (the earlier of the old expiry and the renewal's start), named by `carried_transaction_id`. Plan reads grant the carried plan until then unless that transaction was refunded. The cron's lapse sweep re-derives the plan once the carry ends (`carriesEnded` in its response) and clears it, so the mirror follows within one cron interval.

Sandbox purchases are free, so in production deployments a Sandbox subscription grants a plan only for the App Store bundle `com.cmux.app` and only when the signed-in cmux account's primary email is verified and in `APPLE_IAP_SANDBOX_ACCOUNT_EMAILS` (comma-separated, case-insensitive). Every other TestFlight tester, and every TestFlight purchase of the beta and INTERNAL bundles, is recorded but grants nothing, so the account-token route answers `purchases_unavailable` and lists no products to those builds. The grant check reads the email from the account when a Sandbox row would otherwise grant, so removing an email from the list ends that account's Sandbox grant on the next plan read. Other deployments grant every Sandbox purchase, including staging (`cmux-staging.vercel.app`), which runs with `VERCEL_ENV=production` in its own Vercel project and is told apart by `VERCEL_PROJECT_ID`. `APPLE_IAP_SANDBOX_ENTITLEMENTS` (`all`, `none`, or a bundle list) overrides both, and then the email list is not read.

The production list must contain the App Review demo account `cmux-rev-0e6ba145@mailinator.com` (App Review buys in the Sandbox against production; without it App Review sees no products and rejects the submission) and `lawrence@manaflow.ai`. Production value: `APPLE_IAP_SANDBOX_ACCOUNT_EMAILS=cmux-rev-0e6ba145@mailinator.com,lawrence@manaflow.ai`. Both accounts must exist in production with a verified email; verify the demo account through its public Mailinator inbox.

## Analytics (RevenueCat parity)

Server-side PostHog events, one per App Store Server Notification that changes subscriber-visible state (deduplicated by `notificationUUID`, timestamped at the notification's `signedDate`), keyed by the cmux user id: `subscription_started`, `subscription_renewed`, `subscription_plan_changed`, `subscription_cancel_scheduled` (auto-renew off), `subscription_resubscribed`, `subscription_billing_issue`, `subscription_grace_period_entered`, `subscription_expired`, `subscription_refunded`, `subscription_revoked`. Properties: `source` (`apple` | `stripe`), `plan_id`, `product_id`, `billing_period` (`monthly` | `yearly`, Apple events), `storefront`, `currency`, `price` (gross, local currency), `price_usd_estimate`, `net_usd_estimate` (commission 30%, or 15% after one year of paid service), `environment`, `original_transaction_id`. Apple events also carry `notification_type`, `notification_subtype`, and `auto_renew_product_id`. Mapping: `SUBSCRIBED` (`INITIAL_BUY` started, `RESUBSCRIBE` resubscribed), `DID_RENEW` renewed, `DID_CHANGE_RENEWAL_PREF` plan_changed (`UPGRADE` takes effect now, `DOWNGRADE` at renewal), `DID_CHANGE_RENEWAL_STATUS` `AUTO_RENEW_DISABLED` cancel_scheduled, `DID_FAIL_TO_RENEW` (`GRACE_PERIOD` grace_period_entered, otherwise billing_issue), `EXPIRED` expired, `REFUND` refunded, `REVOKE` revoked. `GRACE_PERIOD_EXPIRED`, `REFUND_REVERSED`, `PRICE_INCREASE`, `RENEWAL_EXTENDED`, auto-renew re-enabled, `CONSUMPTION_REQUEST`, and `TEST` update state (or are only recorded) without an event.

`subscription_entitlement_granted` is sent after a transaction is recorded and applied, from both the app-posted route and the notification, when that subscription is the plan the user now holds through Apple (so a Sandbox purchase that grants nothing sends none). Properties: `source` (`apple`), `plan_id`, `product_id`, `billing_period`, `environment`, `original_transaction_id`, `transaction_id`, `status`, `expires_at`; `distinct_id` is the cmux user id. The insert ID is `apple_entitlement:<transaction id>`, so the app post and the notification for one transaction count once, and each renewal counts again. The lifecycle events above come only from notifications, so a deployment whose App Store Server Notifications URL is missing records purchases with no lifecycle events; the grant event does not depend on notifications. The `price_usd_estimate` is exact for USD storefronts and the plan's US list price elsewhere. Stripe does not emit these events yet; it keeps its existing `cmux_billing_*` events.

The cmux-admin app page `/subscriptions` (data from `GET /api/admin/subscriptions/analytics`) shows, filterable by source and plan: active subscriptions, MRR gross and net, new subscriptions, churn, refunds, billing-issue and grace counts, revenue by storefront, and monthly cohort retention. Sandbox data is excluded unless toggled.

The iOS app sends client events (`ios_paywall_viewed`, `ios_purchase_started`, `ios_purchase_cancelled`, `ios_purchase_failed`, `ios_purchase_pending`, `ios_restore_started`, `ios_restore_completed`) through its existing analytics path (`/api/analytics/events`, which accepts only allowlisted `ios_`-prefixed names in `web/services/analytics/iosEventPolicy.ts`) so the paywall funnel joins the server lifecycle events. Properties: `entry_point` (`settings` | `cloud_upgrade`), `product_id`, `plan_id`, and `reason` on failures; `success` and `restored_count` on `ios_restore_completed`.

## Plan allowances

App Store and web subscribers get the same allowances, each reset by its own subscription period (App Store: newest transaction's purchase date to expiry, extended by a grace period; a yearly subscription resets monthly from its start date). Go: one saved Cloud VM (running or paused), up to 8 vCPU / 16 GiB, no monthly hour cap (`web/services/vms/README.md`). NEXT plans: the machine-minutes in the table above.

The Pro and Max allowances below are **off by default**: https://cmux.com/pricing promises no hour limits, so without `CMUX_VM_PLAN_BUDGETS=on` no Pro or Max user gets a compute-hour or disk limit and the 402 refusals never fire. With the switch on: Pro: 375 compute-hours and 160 GB of disk across saved machines. Max: 1,500 compute-hours and 640 GB. A compute-hour is 1 vCPU with 2 GB of memory running for one hour (a machine draws `max(vCPUs, memory GB / 2)` units). Create, resume, fork, and restore refuse with 402 `vm_compute_budget_reached` (with the reset date) when the compute-hours are used up, and create or disk growth refuses with 402 `vm_storage_budget_reached`; the minute job pauses running Pro and Max machines at the limit. Founder's Edition, operator plan grants, and Team have no allowance (an operator grant to a user who also holds a Pro or Max subscription is metered by that subscription). A machine is metered at its current recorded shape, so resizing a machine also re-rates its earlier runtime in the period. `CMUX_VM_PLAN_BUDGETS=on` turns them on.

## CI

Pull requests that touch billing run the Billing lane (`.github/workflows/billing.yml`): every billing unit, database and server end-to-end story test, picked by `scripts/ci/billing_lane.py`.

The Billing nightly (`.github/workflows/billing-nightly.yml`, 09:41 UTC on main) adds what is too slow or depends on Apple:

- the whole Billing lane on main's HEAD, whatever changed;
- an Apple delivery round trip for `com.cmux.app` in Sandbox and Production: the App Store Server API sends a TEST notification, the job waits until Apple reports it delivered to `/api/billing/apple/notifications`, then reads `GET /api/cron/apple-notifications/health?uuid=<notificationUUID>` (`Authorization: Bearer $APPLE_NOTIFICATIONS_HEALTH_TOKEN`) to confirm the ledger recorded it. The read answers only for TEST notifications, with `found`, `environment`, `receivedAt`, `processed` and `processedAt`; without `APPLE_NOTIFICATIONS_HEALTH_TOKEN` in the deployment it answers 503;
  Before the first App Store release the Production request answers HTTP 401 (see Production API before the first release). The job then probes the Sandbox with the same key: when the Sandbox answers and the repository variable `APPLE_IAP_PRODUCTION_RELEASED` is not `1`, the Production job passes with a neutral note ("locked until the first App Store release") in its summary and a `::notice` annotation, so the night stays green. When the Sandbox refuses the key too, or once `APPLE_IAP_PRODUCTION_RELEASED=1`, the 401 is red. The nightly's key is an In-App Purchase key, which cannot read App Store Connect, so the release is recorded by hand in that variable;
- an App Store Server API status lookup of a known Sandbox subscription (`vars.APPLE_IAP_HEALTH_ORIGINAL_TRANSACTION_ID`);
- the StoreKit simulator suite (`BillingStoreKitTests`), dispatched on feat-cmux-next, where the iOS billing client lives.

A red night opens or updates the issue "Billing nightly is red" and posts to #cmux-automations on a state change. The Apple checks skip, green, until the `billing-nightly` GitHub environment (deployment branches: main) has `APPLE_IAP_KEY_ID`, `APPLE_IAP_ISSUER_ID`, `APPLE_IAP_PRIVATE_KEY` (the server values above), `APPLE_NOTIFICATIONS_HEALTH_TOKEN` (the production deployment's value) and `CMUX_NOTIFY_TOKEN`.

### After the first App Store release

Once `com.cmux.app` has its first App Store release (1.0.0 is manual release; do this the day it goes live), run the post-release check:

```bash
gh workflow run billing-nightly.yml -R manaflow-ai/cmux --ref main -f post_release_check=true
```

Its `apple-post-release` job (the `billing-nightly` environment's secrets, so main only) runs `bun scripts/billing/apple-nightly-check.ts post-release --bundle-id com.cmux.app --health-url https://cmux.com/api/cron/apple-notifications/health`, all in Production with no lock fallback, and prints pass or fail per step in the job summary:

1. **delivery**: the App Store Server API sends a Production TEST notification and reports a `SUCCESS` send attempt to `/api/billing/apple/notifications`.
2. **stored**: `GET /api/cron/apple-notifications/health?uuid=` shows cmux.com recorded it as `Production`.
3. **history**: a Production Get Notification History call for the last day answers.
4. **cursor**: `GET /api/cron/apple-notifications/health?cursor=Production&bundle=com.cmux.app` (same token; timestamps, the stall count and an opaque `position`, never Apple's pagination token) shows the Production backfill cursor move: a first cursor, a new window, or a new page. The cron runs every 30 minutes, so this step waits up to 35.

The same command runs from a shell with the four `APPLE_IAP_*` / `APPLE_NOTIFICATIONS_HEALTH_TOKEN` values in the environment. When every step passes:

1. Set the variable so a Production 401 is red from now on: `gh variable set APPLE_IAP_PRODUCTION_RELEASED --body 1 -R manaflow-ai/cmux`.
2. Check that `billingHealth.appleServerApiProduction` in the admin analytics response reads `ok`, and that the cron's `productionApi["com.cmux.app"]` is `ok`.

A failed **delivery** with HTTP 401 means Production still refuses the key: confirm the release is live in App Store Connect and that the key's team owns the app. The first backfill runs catch up from 178 days back, one day window at a time.

### Manual release checklist

Real purchases need a device signed in to a Sandbox tester account, so CI does not make them. Before an App Store release, on a device with a Sandbox tester (App Store Connect > Users and Access > Sandbox):

1. Buy each plan in the build under review; the Plan screen and `/api/billing/apple/account-token` show it within a minute.
2. Let a monthly Sandbox subscription renew (Sandbox renews every few minutes) and see the renewal in `apple_notifications`.
3. Cancel it in Settings > Apple ID > Subscriptions and see access end at expiry.
4. Restore purchases after reinstalling the app.

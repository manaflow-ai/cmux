## User acceptance runs

Two complete engaged simulator runs are required, each at least 3,600 seconds of actual foreground use. Use the deployed staging backend for automatic/direct-capable mode and the deployed production backend for relay-only mode. Also run a real-client smoke in staging relay-only and production automatic mode, so both deployments exercise both modes. Production uses only the designated test team and v2-scoped records in the existing production database. Development namespaces remain isolated from production traffic.

Run an isolated tagged Mac and isolated simulator using the configured `agent` Stack profile. Record the leased fleet host, simulator UDID, Mac/iOS bundle IDs, tag, source SHA, built artifact hashes, backend URL, Worker version, database identifiers and relay release. Never use the user's active cmux or a shared simulator. A physical iPhone does not substitute for the explicitly requested simulator run; any repository-required phone handoff is additional and uses the `personal` profile with a matching Mac.

## Exact measurement contract

Each client event includes run ID, source/build identity, process ID, monotonic timestamp, environment, verified team/user opaque IDs, device identity reference, peer reference, connection-attempt ID, peer session ID, endpoint generation, control-socket generation, operation/request ID, event/reason and result. Record wall time for correlation, but never subtract clocks from different machines to compute latency. Use local elapsed time or paired request/response measurements.

Required counters for every run:

- Initial peer admissions, later admissions, peer session ends, automatic redials, endpoint closes/rebinds, explicit revocations and selected-path changes, attributed to both peer and lifecycle window.
- API and relay renewal attempts/successes/failures, successful installs, expiry crossings, old/new overlap and retry delays. Record accidental Stack checks on ordinary operations separately.
- Control socket opens/closes/replacements, request timeouts, HTTP fallbacks, denied/limited operations, directory gaps/resyncs and output-bound hits.
- Terminal lane opens/closes, cursor gaps, input sequence acknowledgments, workspace operations and maximum observed input-to-result delay during renewal versus the same workload outside renewal.
- First dial, peer admitted, first workspace response, list rendered and first usable terminal timestamps for each launch; background/foreground and resumed usable timestamps for each resume.

The run fails if a required counter is absent or stops updating. Video without connection identity cannot prove no reconnects; journal counters without real UI use cannot prove usability. Record clock source, sampling cadence, event loss and log rotation. Screenshots with different hashes are supporting evidence only. Use a stable known workload and sequence markers to detect omitted/duplicated terminal data.

Capture continuous video in bounded segments, dense frame splits around launches/renewals/resumes, contact sheets and representative frames. Preserve every segment's timestamps and join order. Profile the same stimulated path with Instruments or the appropriate platform profiler, recording target PID/tag/UDID and CPU, memory, main-thread stalls, network latency and energy-related repeating work. Include a quiet connected period to demonstrate that no application presence timer prevents DO hibernation.

## Decisions that must become concrete before final verification

Record the exact identity tuple and canonical signed bytes; explicit device permission policy; team-switch/publish UX; membership removal delivery and maximum stale-authority interval; offline peer-permission lifetime; global EndpointID reservation/recovery protocol; shared user counter authority and failure behavior; physical storage/memory guards and shared-record attribution; transport ping/failure timing; relay audience and key rotation; retained security-history limits/backups; observability retention/alert thresholds; branch lifetime/deletion policy; and old-service retirement timing. They were open in revision 21. Choosing them is implementation work, not grounds to omit them from completion.

Existing verification is insufficient: `scripts/irx-soak.py` assumes a 15-minute run, a 3,000 ms admission threshold and five-minute relay tokens. It does not measure launch-to-rendered-workspace-list, one-hour tickets, required background recovery, a new backend/resource identity, Zod contracts or this team's permission model. Adapt the behavior harness and inspect its analyzer before trusting a PASS. Source-pattern checks alone cannot replace runtime evidence.

## Final evidence packet

Use one manifest row per criterion/scenario: `criterion -> artifact -> captured source SHA -> Mac/iOS hashes -> backend release -> environment -> run ID -> verdict`. Include baseline/head diff, generated-contract checks, test execution counts, runtime reports, redacted deployment receipts, videos/frame sheets, traces, raw timing samples, network/path proof, operation queries, quota/row-count results, and remaining failures. Pin the exact running artifacts; a newly committed change invalidates prior build evidence under the verification workflow.

A fresh final verifier independently reads the criteria, final diff and artifact packet, with no implementer success narrative. Completion requires every criterion proved, no missing or stale evidence, required checks passing and actionable findings resolved. Deploy authorization does not imply PR merge authorization. Open the PR and present the full evidence; merge follows the user's explicit merge directive.

Dictionary: A soak is sustained active use over a measured period. A monotonic clock measures elapsed time without wall-clock adjustments. A canary deploys to a limited test group first. A migration changes stored database structure. Hibernation lets an idle Durable Object stop executing while its sockets remain open.

Why a challenge?

Stack authenticates the user and provides team membership. The challenge proves that the registering app also holds the private key for the advertised IROH EndpointID. Signing a fresh nonce and the registration payload stops someone from registering a copied public key or replaying an old enrollment.

Current: each signed registration, including route refresh, requests a five-minute challenge. Successful registration deletes that challenge; issuance still inserts separate rows, so simultaneous pending challenges can exist.

Proposed: challenge only for enrollment or approved key replacement/recovery. Ordinary resume, ticket renewal, and signed metadata updates reuse the existing binding.

One identity, one device row

Within an environment, Stack project, and team, device records also retain their owner user ID. The proposed identity key is (teamId, ownerUserId, deviceId, appNamespace, devTag). The namespace identifies the app/channel, so INTERNAL, BETA, and App Store stay separate. A dev tag separates simultaneous dev builds.

Repeated registration of the same identity updates its current device record. New identities add records subject to device/storage limits. Store endpoint key, identity generation, and optional pending challenge fields on that row. A fresh challenge replaces the prior nonce; consume it atomically with enrollment. Reject it after 30 minutes. The slot can remain until the next challenge replaces it or the identity is removed. No challenge cleanup scan or scheduled deletion is needed.

Use stable app identity, not the app version number. An ordinary update should not create another device identity. The app-instance identifier is metadata, not another accumulating row key.

Pairing is off until the user enables it

Decided: each Mac must have Enable iOS pairing turned on in cmux Settings before its IROH features run. Check that local setting before initializing the endpoint or starting any IROH backend task. While off: no IROH listener, relay connection, control socket, enrollment, directory fetch, or credential-refresh loop. Other cmux features keep their own independent network behavior.

Once enabled, a returning Mac immediately starts IROH from usable cached data while restoring backend control and refreshing credentials in parallel. First enrollment still obtains the missing prerequisites. Re-enabling an intact trusted identity resumes it. Disabling stops IROH listeners, sessions, and renewal/reconnect tasks; delayed callbacks must not start them again. Detailed migration and cleanup behavior remains an implementation decision.

Proposed iOS onboarding text: “On your Mac, open cmux Settings and turn on Enable iOS pairing. Select the same team on both devices using accounts allowed to connect.”
Proposed empty computer list: “No Macs found. Open cmux Settings on your Mac, enable iOS pairing, and select the same team on both devices.”

No scheduled DO presence heartbeat

Accepted removal. A usable authorized IROH session determines whether this client is connected. A saved Mac without an active session has unknown reachability. Never hide it or block cached dialing based on a backend online flag. Keep control sockets for credentials, directory updates, and revocation; their status describes backend connectivity only.

Keepalives exchange traffic in both directions. In IROH’s QUIC transport, either endpoint can send a probe and the peer acknowledges it. This does not require duplicate application timers. Keep the library’s transport liveness and application request deadlines. On the backend WebSocket, a native client can ping and Cloudflare automatically returns pong without waking the DO. Exact intervals, sender configuration, and failure policy remain open. QUIC PING/ACK · WebSocket ping/pong.

Keep a bound on unsent outgoing data

Accepted generous starting bounds: A slow phone must not make the server accumulate unlimited unsent messages. Bound queued and transport-buffered bytes, pause production where possible, and resync the control socket when required. This does not limit total messages delivered or terminal output. Allow up to 1,024 unsent messages or 2 MiB per connection, with a total of 4,096 messages or 8 MiB per user, whichever is reached first. Allocate memory only as needed. These starting sizes are increased eightfold; tune them after measuring real payloads. A shared DO also needs a physical memory safeguard that handles slow consumers fairly.

IROH has one connection coordinator per peer to avoid duplicate callers, while permitting parallel direct/relay paths, independent peers, and a planned replacement beside a healthy session. No local attempts-per-minute quota is added. Local cache reads, credential installation, server replies, and database calls behind an accepted request have no additional request counter.

User limits by endpoint and message

Decided: each client endpoint or message type gets its own generous per-user allowance, with no IP quotas. Registration is accepted at 300/hour, burst 50. Other numerical allowances remain recommendations. All devices, builds, and Dashboard sessions belonging to the same user share that user’s operation allowance across teams within an environment. A socket message and its equivalent HTTP fallback share that same allowance. Development and production have separate budgets.

Each allowance refills at the stated rate. “Burst” is how many requests can arrive together after idle time; unused allowance cannot accumulate beyond that burst. There are no additional per-device request quotas or daily lockouts. One connection owner per peer prevents duplicate callers while allowing parallel paths and make-before-break replacement. Message sizes remain bounded.

Room for many builds: Seven continuously active app instances need about 7.6 API-ticket renewals/hour and 16.8 relay renewals/hour, with no scheduled DO presence messages. Proposed user allowances are 1,200/hour for each credential type. Generous limits do not increase the normal renewal frequency.

Separate allowance for each client operation. Directory reads, metadata changes, preferences, and revocation each have their own user counter. The key is (environment, Stack project, verified user, operation). Switching teams does not reset it. Versions of the same operation and its HTTP fallback share one policy. Route parameters such as a device ID never create fresh allowances.

Local work, server responses, and database calls behind an accepted request have no separate request quota. Message sizes, queued bytes, and open-connection counts remain resource bounds. Message names and unmapped fallback routes are still working design details.

Scheduled application presence is removed. Protocol ping/pong needs no application counter: Cloudflare handles it without waking the DO. Actual socket-close cleanup and enforcement of known revocations must always run. Cloudflare ping/pong behavior.

The client owns credential renewal

One current cached value: each device/build keeps an API ticket per team authorization scope and a relay credential per relay audience (the relay or fleet that accepts it). Keep the previous valid credential while installing its replacement. Replacing the cache does not invalidate previously issued signed tokens; they can remain valid until expiry, subject to applicable revocation checks. No database row per issued credential and no credential-deletion job.

One client coordinator schedules API-ticket and relay-credential renewal. It requests a replacement over the control socket before expiry. The DO checks current permission and issues the replacement; it does not run a second renewal timer for each client.

The client installs the new credential, switches when it is usable, and briefly retains the still-valid old one for ongoing work. The server permits that bounded overlap. Failed renewal backs off and retries without restarting a healthy IROH session. Neither side extends expired authority; explicit revocation takes effect independently.

IROH starts immediately with cached data

Returning Mac and iOS clients start IROH and backend refresh in parallel. Use the saved identity, usable cached relay credentials, relay URLs, and still-valid peer permissions without waiting for the control socket, ticket renewal, or directory refresh. A healthy peer connection continues while refresh runs.

Fresh credentials update the shared credential state and promptly unblock a retry that needed them. One coordinator owns retries. First launch, or loss of required saved identity data, must complete the missing enrollment and credential steps first. Network and peer availability can still affect success.

What are “hints”?

For v2, a hint means the reachable relay server URL. We may keep more than one relay URL for fallback. A relay hint helps find the app; it does not grant terminal access or prove EndpointID ownership.

Direct mode addresses, direct ports, and optional direct IROH paths stay local or move directly between peers. They are not stored in the server registration.

A relay credential is permission to use the relay service. It is separate from the hint and from terminal permission.

When the Mac registers today

The code also calls updates to an existing device record “registration.” Those updates normally keep the same registered identity.

  1. When the connection system starts after launch/sign-in, register before getting relay credentials.
  2. After IROH starts, update the record with the actual relay and connection ports.
  3. After a credential renewal, check the connection details. Publish again if they changed, or the previous publication is at least 15 minutes old.
  4. Switching teams, restarting the connection system, or re-enabling networking repeats setup. An incomplete setup can retry.

Separate “still online” messages run every 15 seconds. Silence for 45 seconds marks the Mac offline. A clean shutdown says “going offline” immediately. These messages do not create a new device identity.

Yes, iOS registers too

The Mac needs to know that the connecting phone belongs to the team, even though the phone does not advertise itself as a Mac to connect to.

  1. First setup after sign-in: register before obtaining relay credentials and the device list.
  2. On a later app launch: refresh registration during setup. With usable saved data, that refresh happens in the background.
  3. Missing saved identity or device-list information, or unusable saved relay credentials, makes the current code register before finishing setup.
  4. Account changes or rebuilding the connection system repeat setup. Incomplete setup is retried.

Returning to the foreground with the connection system still alive checks credentials and reconnects. It does not by itself call registration. Connecting to another Mac or opening another terminal reuses the phone identity.

Shared types and server validation

Updated decision: use Zod instead of Ajv. Author versioned request and response schemas in Zod. Zod validates server inputs and outputs; export JSON Schema at build time and use quicktype to generate Swift and TypeScript models. Clients decode generated types and handle server errors. They do not run schema validators.

Keep a portable JSON shape for the shared contract. Request and response schemas are separate; avoid coercions and transforms that change the wire type. Keep custom server checks, such as team permission, signature, or cross-field rules, explicitly documented. Fail generation for an unrepresentable shape instead of silently exporting unrestricted data.

Each method/frame carries its schema ID. Compatible additions preserve old behavior; breaking request/response changes or intentional behavior differences for newer clients get a new handler version. Keep supported App Store versions working. No mandatory startup version exchange; app version can accompany an ordinary request. Retired versions receive client_upgrade_required with the agreed long backoff.

EndpointID ownership

Every unique identity tuple owns one EndpointID. The active map is keyed by EndpointID and stores its environment, Stack project, team, owner user, device, app namespace, build tag, platform, and generation.

Registration and key replacement reserve this key atomically. No other device, build, or environment may reuse it. Team-local Durable Object SQLite stores the full device record; PlanetScale stores the strongly consistent global map.

Security and cost tradeoffs

  • One-hour API tickets remove Stack calls from ordinary backend operations. The team DO still checks the current device generation and revocation state before allowing protected actions.
  • 30-minute relay credentials reduce routine mint traffic. A disconnected relay verifier can accept an already issued token until its expiry. Stopping future minting does not erase that token.
  • Relay access grants transport service, not terminal authority. The Mac must independently authorize the peer against its trusted device list.
  • Online revocation pushes can close sessions immediately after receipt. A disconnected Mac has only its cached list, so the offline authorization lease determines the stale-access window. The main value of 24 hours is a separate v2 decision.
  • Use one pending challenge field set per identity, bounded user rate counters and audit retention. An enrollment challenge request is rate limited before allocating a pending-only device row.
  • Preserve cached state through recoverable outages; never reconnect all IROH sessions just because a backend credential refreshed.

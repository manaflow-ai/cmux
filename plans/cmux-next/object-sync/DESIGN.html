Object sync: one protocol for Mac, iPhone, web and Chief, with the Mac off

Status: design for review, 2026-10-18 (object-sync lane). Base read: origin/feat-cmux-next 7a440f4cd52d, origin/feat-cnx-ios 3d1255930b42, PR 20414 (Mac host), PR 20993 (CnxChief on cloud-api). Binding inputs: spec sync-and-transport.md (draft 2), OWNERSHIP-PRINCIPLES.md, ownership-v2.md, home-messaging.md, transport.md, state-placement.md, remote-state-ownership.md, mobile-rust-core.md (MOBILE-RUST-1..5), and Lawrence's standing rules (decouple from Swift, one protocol for web and native, shared Rust mobile core, many Chiefs on one conversation model, two Chief brains).

The ask (Lawrence, 2026-10-19): "We need to have a macOS build that is synced to the iOS build properly and then I need to be able to see that I can send messages and they are all individual objects ... that communicate with each other. So I can have all the workspaces syncing ... I should talk to durable objects so that even if my Mac is off I should be able to use it ... from first principles, and not do anything hacky. Do not care about old code."

0. Summary

  1. "The protocol Aziz uses for syncing everything" (cnx, feat-cnx-ios) is not a sync protocol. It is a tunnel. A Cloudflare Worker with one TeamHub Durable Object per team does presence, WebRTC/WireGuard signaling and a datagram relay. The phone dials the Mac, and every read and write (workspaces, tabs, terminals, agent chats, Mac Chief) goes through the tunnel to the Mac's cmux-tui daemon, chief socket and acpmux. The Mac is the only source of truth. With the Mac off, the phone shows a stale local JSON snapshot and can do nothing. The phone also discards the daemon's deltas and refetches the whole workspace list on every event.
  2. cmux-next already has the right protocol, half built: the ownership wire cmux.wire/1 (backend/packages/ownership, checked by formal/OwnershipConvergence.tla). Every entity has one owner. Owners commit ops with idempotency keys and publish ordered events per stream (seq). Clients hold a confirmed mirror plus an intent log, detect gaps, resume by after_seq, and settle lost replies from the snapshot's decided keys. ConversationDO, UserDO, MuxDO, TeamDO, CloudDO speak it today. PR 20993 put the phone's Cloud Chief on it.
  3. Decision of this design: every object has exactly one home. Durable, shared, social and agent state is homed in a Durable Object, so the phone works with the Mac off. Machine-bound state (PTYs, files, local agent processes, the layout of workspaces whose terminals run on that Mac) is homed on that machine, and the machine publishes a read replica of it to its HostDO. With the Mac off, the phone reads that replica with an honest offline since state and cannot write to it (no fake success). Nothing is a CRDT. Nothing is mirrored by a Swift adapter.
  4. One wire for everyone: Mac app, iPhone, web, TUI, CLI, the Mac daemon and the Cloud Chief speak cmux.wire/1 frames. The Mac app speaks it to its local daemon. The daemon, the phone and web speak it to the DOs. The phone runs the same Rust client core as the daemon (cmux-cloud-wire stream mirror, bound by uniffi), so no sync logic is written in Swift or Kotlin.
  5. The direct phone-to-Mac link (cnx WireGuard/WebRTC) is kept only as a data-plane fast path for live terminal bytes, browser video and file transfer, which the DO relay can also carry. No state, no command and no conversation ever needs it.
  6. Phase 1 (started in this lane): the Rust stream mirror in cmux-cloud-wire, a port of the TS ProjectionClient in effects mode with the same frame types, gated by conformance vectors exported from the TS engine. It is the one client core that the Mac daemon, iOS and Android will use.

Not principled (the reasons this design replaces parts of it):

  • Two sources of truth for Chief (Mac chief over the link, Cloud Chief on ConversationDO), each with its own outbox file.
  • Two backends with duplicated identity: cnx-ios-api (Postgres devices, TeamHub presence) next to cloud-api (UserDO installs, TeamDO members and hosts, PairingDO, HostDO relay).
  • Snapshot-on-every-event workspace sync with no revision check; O(tree) per title change.
  • Policy written twice (hostd/src/policy.rs mirrors Swift DaemonLanePolicy.swift).
  • No cloud state at all, so "Mac off" is a dead end by construction.
  • Error detection by string matching ("401", "4002 "), runtime ALTER schema changes, owner keys packed as projectId:sub, unsupervised hosts with no pairing.

Principled and worth keeping: userspace WireGuard with roaming, TURN-first fallback and reachability markers; the input lane and the per-class send queue (no head-of-line blocking for keystrokes); the media lane for browser video; Secure Enclave phone keys with Face ID approval for risky answers; Mac identity pinning; content-minimized push (the Worker writes the text, the Mac sends only a kind and a place); Server-Timing on every response; locationHint from the client's location.

3. First principles

  1. One home per object. A fact has exactly one writer: a DO or one machine's daemon. Everyone else holds a mirror. (OWNERSHIP-PRINCIPLES, spec 2.)
  2. Home follows the resource. State that only exists while a machine runs (a PTY, a file, a local process) is homed on that machine. State that must outlive any one machine (conversations, Chiefs, runs, the workspace registry, devices) is homed in a DO.
  3. Reads never depend on the home being up. Every machine-homed stream is replicated to that host's HostDO (snapshot + bounded tail). Writes always go to the home, and are refused honestly when it is unreachable.
  4. One wire. Every owner speaks the same frames. A client is the same state machine whether the owner is a DO, a daemon on the Unix socket, or a daemon behind HostDO.
  5. Server-ordered ops, not CRDTs. Each owner orders its own stream. Conflicts are resolved by the owner's reducer (reject, expected_revision, or a commutative rule such as max for cursors).
  6. Logic once, in Rust or in the owner. Swift and Kotlin render and send intents. The TS DO reducers and the Rust mirror are kept equal by conformance vectors.
  7. Control plane and data plane are separate. State and commands go over the wire to owners. Bulk live bytes (terminal output, video) go over channels that may take a direct path.
  8. Event-driven only. No polling, no timers as synchronization; DO alarms only for owner work (outbox drains, retention, wake retries).

5.1 Workspaces: record in the cloud, contents at their home

A workspace is two objects:

  • The workspace record lives in the cloud directory (TeamDO rows, personal team for a single user): id, name, color, icon, home (host:<h> or cloud), its workspace conversation id, a status summary (agent state, unread, last activity) published by the home. This is what the phone's workspace list renders, and it is always available.
  • The workspace document (layout, tabs, references to terminals and agent sessions) is owned by its home. A Mac workspace is homed on that Mac's daemon, which keeps Cmd+D local (B1 budget, remote-state-ownership.md). The daemon publishes doc:<ws> events to HostDO, which keeps the snapshot and tail, so the phone renders the layout with the Mac off and marks it offline.
  • A workspace whose terminals run in the cloud (Cloud VM, team VM) or that has none yet ("conversation-first" workspaces created from the phone) is homed in DocDO and is fully editable from any device.
  • Moving the home (workspace.move_home {to}) is an explicit op, like conversation.promote: the old home freezes the document at a seq, the new home starts from that snapshot, the directory row flips. Terminals never move (data-model.md 1.2a); a moved workspace references them remotely.

5.2 Hosts (remote hosts joining the tailnet)

Lawrence, 2026-10-18 (via the coordinator): Linux, Windows and macOS hosts join the network; each host is a sidebar group that shows exactly its sessions; hosts are discovered and synced across all of the user's clients. The companion design is plans/cmux-next/remote-hosts/DESIGN.md (another lane); this section fixes only the object model it plugs into.

  • A host is one object with two parts: the record (host_…: name, platform, owner user, team, enrolled by which install, capabilities, reach policy) is a row of the TeamDO directory (team:<t> stream), and the live part (presence, replica of its host-homed streams, relay, forwarded ops) is its HostDO. The Mac is a host like any other; so is a Cloud VM.
  • Discovery = the directory. A host appears on every client of the user when its enrollment commits in TeamDO (host.enroll, by the host's daemon install after the user approves it on a signed-in client, or by the device flow on a headless Linux box). No client scans the network. Network reach (tailnet address, WireGuard key, endpoints) is a field of the record that the transport reads; it is not how clients learn that a host exists.
  • The sidebar group of a host is a projection: the rows of host:<h>/session (its terminal sessions and workspaces homed there), served live by the host, or from HostDO's replica with owner.status offline since when it is off. A client never merges two hosts' lists into one owner.
  • Group order, collapsed state and which hosts are hidden are the user's organization. Today data-model.md 1.2(c) keeps personal organization only in the Mac's home session. Lawrence's "synced across the user's clients" moves it to the user's own stream: a sidebar document in UserDO (user:<u>), one writer (UserDO), every client a mirror. Per-device state that must not sync (window frames, scroll, which pane has focus) stays on the device.

5.3 Identity and versions that UI animation and sizing can rely on

The sync UX design (plans/cmux-next/sync-ux/DESIGN.md, another lane) animates renames and reorders keyed by stable object ids and picks multi-client sizing policies. The protocol gives it:

  1. Stable ids. Every object (workspace, tab, pane, terminal, host, message, conversation) has an owner-assigned id that is never reused or renamed. A rename changes a field, never the id. An optimistic intent gets a client-minted id in the client's namespace (client id + UUIDv7, remote-state-ownership.md A2) that the owner accepts as the final id, so a pending row becomes the confirmed row without a key change (no remount, no flash).
  2. One change, one event. Every event names its stream seq and, in effects mode, the exact rows written (writes: [{table, key, n, row}]). A client diffs per key: a write that changes only order_key is a reorder; one that changes title is a rename; a delete is a removal. No client diffs whole lists.
  3. Explicit order. Ordered collections that people rearrange (sidebar groups, workspaces, tabs) carry an order_key (a fractional index string, as cmux-layout-reducer::sidebar_doc::order_key does already), so a move is one row write and two clients' moves never renumber siblings.
  4. Per-object revision. Each row carries rev = the seq of the event that last wrote it, so a client can drop a stale optimistic animation (its intent settled at a lower rev) and order animations from different streams per object.
  5. Origin and actor. Events carry actor and origin (user, cli, mcp, script, remote), so the UI can animate a remote change (another device, an agent) differently from the local user's own change, which was already shown optimistically.
  6. Sizing. Terminal size is owned by the session host (spec 3.4): clients send presence.set {viewport {cols, rows}, visible, active}; the host computes the canonical grid by its policy and publishes it as a terminal field; the presence frame lists every attached client's viewport. The policy itself (minimum of visible viewports, the active client wins, or a per-terminal pin) is a host setting that the sync UX design chooses; the protocol needs no change for any of them.

Every workspace gets a conversation (conv_…, kind workspace) in ConversationDO at creation. That is where the phone talks to the workspace and its agents with the Mac off; the Chief and agents read and post there; the Mac shows the same thread. This is the "messages to a workspace" path of the acceptance test.

6. Sync protocol

The protocol is cmux.wire/1 as implemented by backend/packages/ownership and specified by spec sync-and-transport.md section 3. This section lists only what this design adds or fixes.

6.1 Frames (unchanged)

Client: hello, subscribe {stream, after_seq?}, unsubscribe, op {op, params, idempotency_key, origin, expected_revision?}, snapshot.request {pending[]}, rpc (at-most-once runtime commands such as terminal.input), presence.set, channel.open/credit/close. Owner: welcome, snapshot {stream, seq, state, decided[], rows?}, event {stream, seq, tx, op, params, actor, origin, at, effects?}, result, reject, request-settled {stream, sequence, ok}, owner.status {stream, status, since, cached_seq?}, presence, rpc.result.

6.2 Client state machine (the Rust mirror, phase 1)

Per stream: confirmed {state, seq}, loaded rows, pending intents (ordered), held settles, buffered events, awaiting flag. Rules (equal to ProjectionClient):

  • An event with seq = confirmed.seq + 1 applies. Row-mode owners send effects {state, writes}, which the mirror applies without running the reducer; JSON-mode streams carry the op, and a mirror that has no reducer for that domain asks for a snapshot instead (effects mode is the default for every new owner, so mirrors in any language need no reducers).
  • seq > confirmed.seq + 1 is a gap: buffer it and send snapshot.request {pending keys}.
  • request-settled ok settles an intent only once the mirror reached its sequence (held until then), so the UI never flickers back to pre-op state.
  • Snapshot: replace confirmed state and rows when snap.seq >= confirmed.seq, drop decided keys from pending and expired, then replay buffered events.
  • Reconnect: resend every pending intent with its original key, then request a snapshot. Intents older than 24 h expire and are shown, never resent (owners keep decided keys 7 days).
  • Visible state = confirmed + pending intents rendered from their params (a pending bubble, a greyed new tab). Optimistic local layout (Cmd+D) is the home's job, not the mirror's: the Mac daemon is the home of Mac layout.

6.3 Cursors, backfill, history

  • Resume: subscribe {after_seq}; the owner replays from its event window (30 days or 10,000 events, E3) or answers a snapshot when the cursor is older.
  • Row-backed history: a snapshot carries the newest rows (message tail); older pages come from the read conversation.history {before_seq, limit}. Add conversation.since {after_seq, limit} (asked in ownership-v2.md 3.4) so a client catching up on a conversation it is not subscribed to needs no socket.
  • Inbox-driven catch-up: a client subscribes to inbox:<u> always and to at most N hot conversations; inbox.bump {last_seq} tells it which conversations moved; it fetches ranges.
  • Host replicas: HostDO serves subscribe host:<h>/session, doc:<ws>, host:<h>/acp from its stored snapshot and tail when the host is offline, with owner.status offline, cached_seq. When the host reconnects it sends resume {stream: last_published_seq}; the HostDO asks for what it lacks; clients receive the new events with no gap because the host's seq is the stream's seq.

6.4 Conflict rules

  • Single writer per stream, so there are no concurrent writes to merge. Two devices that send conflicting intents get them ordered by the owner; the second may be rejected (revision.conflict with expected_revision, or a reducer rule).
  • Commutative fields use commutative rules: read cursors are max; reactions are a set keyed by (author, part, kind); inbox bumps apply only with a newer rev.
  • Layout ops carry the ids they act on (pane id, tab id), never indexes, so an op on a moved tab still applies or is rejected with a reason (cmux-layout-reducer already rejects unknown ids).

6.5 Offline behavior (U5 and one proposed exception)

  • Owner unreachable (no network, or the host is off): the op is refused at once with owner_unreachable; the control is disabled and says why ("Your Mac is offline since 21:04"). Intents sent before the drop stay pending and are resent on reconnect with the same key.
  • Drafts are per device and never lost.
  • Proposed exception (decision L2): message.send may wait in the device outbox while the device itself has no network, because ConversationDO dedupes by client_msg_id and a message is an append (no invariant can be broken by sending it later). The bubble shows "Waiting for network", and the intent TTL (24 h) still applies. This matches what people expect from Messages and what cnx's Chief outbox already does, but it relaxes U5, so Lawrence decides.

8. Transport

  • Control plane: one WebSocket per device. Target: the UserDO gateway multiplexing every stream the device subscribes to (spec 5). Today: one socket per owner (/v1/wire/user, /v1/wire/conv/<id>, ...). Phase 3 adds the gateway; the frames already carry stream, so clients only change the URL. Hibernation keeps idle sockets free; WebSocket pings are runtime auto-responses (no DO wake).
  • The Mac daemon keeps one outbound socket to its HostDO (it exists for the relay) and adds the publisher role: it pushes events of its host-homed streams, answers forwarded ops and rpc, and serves channel.open. No inbound port, no pairing step for state.
  • Data plane for live bytes: a channel ticket minted by UserDO (/v1/wire/ticket exists) opens a WebSocket to HostDO, which splices it to a link sub-channel on the host. Fast path: when the phone and the Mac can reach each other (same LAN, punched UDP, TURN), the same channel rides an end-to-end WireGuard session (cmux-wg, cnx's roaming and lanes). The channel's identity, ticket and framing do not change with the path. Why keep a direct path at all: terminal echo latency (measured TURN 16 ms vs a far Worker relay 240 to 345 ms on 2026-10-13; the HostDO is placed near the host per transport.md 6, so relay cost is mostly the triangle) and video volume (DO relay billing per message). Why not more: everything else is small, ordered and must work with the Mac off, so it belongs to owners.
  • Why not WebRTC as well: one userspace WireGuard stack serves the phone, the Mac, Linux and Cloud VMs (transport.md), so a second transport doubles the test surface for no new path. cnx's WebRTC carrier can stay until the WireGuard path covers the same networks (decision L5).

9. Auth, devices and teams

  • Identity: Stack Auth session (human) or install token (device, daemon), verified by the Worker. Principals are built only by the Worker and never read from frames (types.ts Principal).
  • Devices are installs in UserDO (install_kind mac, ios, daemon, web, vm). The cnx devices table, TeamHub presence and cnx-ios-api device routes are replaced by install records, HostDO presence and TeamDO's host directory.
  • The Mac daemon is enrolled once by the Mac app (install.enroll_local {daemon_pubkey}, ownership-v2.md 3.4) and mints short-lived tokens by challenge. It never holds the Stack session.
  • Phone keys: keep cnx's Secure Enclave identity key and Face ID approval key, registered on the phone's install record. Approval-required ops (Chief question answers that execute, money and destructive ops) carry an approval signature that the owner checks; the Mac no longer has to be the checker, because the owner is.
  • Reach to a host: TeamDO compiles which installs may reach which host (same user by default, team policy later). HostDO admits relay and channel sockets only for those installs. The Mac's WireGuard still drops unknown keys.
  • Teams: TeamDO members and roles; a personal account is a team of one; no project-prefixed owner keys (one Stack project per environment).

10. Chief

  • A Chief is an agent principal (agent_…, class mux) with a record in UserDO and a MuxDO. ConversationDO wakes it (mux.wake on DM, mention, reply). MuxDO decides which brain runs: the cloud brain (ChiefBrainDO, pi-durable) or a local brain on a host that holds the lease.
  • Both brains are ordinary clients of ConversationDO: they read with conversation.snapshot / since, post with message.send under the agent principal, stream progress as run events (run.live, step.delta in PR 20993). The phone needs no Chief-specific path: a Chief thread is a conversation.
  • One memory per Chief: today brainName = agent/conversation gives one OptChat memory per (chief, conversation). The standing rule says one memory per Chief across all its conversations. Recommendation for the brain lane (not changed here): one ChiefBrainDO per agent, conversations as inputs of that one memory, runs keyed by (agent, conversation, seq).
  • The Mac Chief over the cnx chief channel is retired: the local Rust brain posts to the same ConversationDO thread through the daemon's cloud sync, so there is one thread and one outbox.
  • Hands: the Chief's tools call HandDO (cloud sandboxes, VMs) or the Mac's acpmux hand. With the Mac off, a Mac hand answers offline and the Chief can choose a cloud hand.

12. Durable Object scale and cost

  • Storage: 10 GB per object (SQLite). Conversations: p99 1M messages, about 2 GB (home-messaging.md 6). HostDO replica: per host stream one snapshot plus a bounded tail (cap 10 MiB or 24 h per stream, 64 KiB screen per terminal), so a host with 200 terminals stays under 50 MB.
  • Throughput: about 1,000 simple ops per second per object; about 4,000 relayed messages per second per HostDO (transport.md 13.4). Split by entity, never by user: a chatty Chief thread is one object; a team is not one object for messages.
  • Fan-out: an event is sent to each subscribed socket of that object. Large fan-out (a 64-person group) is fine; anything bigger fans out through UserDO inbox bumps (coalesced per drain), not by sockets on one object.
  • Hibernation: subscribers hibernate; pings auto-respond; an idle host costs about nothing (measured object eviction after 30 s, wake 15.5 ms p50). A DO with a pending alarm wakes only for that alarm.
  • Alarms: one per object (AlarmSerial multiplexes): outbox drains, retention, owner-wake retries, HostDO offline detection grace. No alarm is a poll of another system except provider state repair in CloudDO.
  • Cost: requests dominate; batching relay frames cuts billing about 12 times; a phone that is connected but idle costs nothing in duration. Video over the DO relay is the expensive case, which is why the direct path exists.

13. Security

  • Identity only from the Worker; owners re-check membership and grants on every op.
  • Replicas in HostDO are readable only by principals TeamDO allows for that host; the replica holds terminal screen text, which can contain secrets: it is encrypted at rest by Cloudflare, capped, never projected to PlanetScale, deletable by the owner (host.replica.purge), and can be turned off per host (decision L4).
  • Push payloads stay content-minimized (cnx rule).
  • Approval signatures (Face ID key) are checked by the owner that executes the op.
  • Relay and channels carry WireGuard ciphertext or ticket-bound streams; HostDO cannot read relayed WireGuard datagrams; HostDO channel splices for the fallback path are TLS to the edge, plaintext inside the Worker (same trust as every op).
  • No secrets in logs, tokens never in URLs (wire tickets for browsers).

15. Acceptance test

Setup: staging cloud-api, a tagged Mac build signed in as user U with a workspace W (homed on the Mac, one terminal T running top), the phone build signed in as U, Chief C with the cloud brain.

  1. Mac on: the phone shows W with the same title and status, T's live screen, and W's conversation. Measure: Mac title change visible on the phone in < 500 ms p95 (20 samples).
  2. Power the Mac off (or stop its daemon and network).
  3. Within 60 s the phone shows W and T as offline since <time>; T shows its last screen; the input field and new-tab controls for W say "Mac offline" (no spinner, no fake success).
  4. The phone sends m1 to W's conversation and m2 to C. Both are committed (request-settled ok, seq assigned). C replies r2 within 30 s (cloud brain).
  5. The phone asks C to run a task on a cloud hand; the run shows progress events.
  6. Power the Mac on.
  7. Within 10 s of its daemon reconnecting, the Mac shows m1, m2, r2 and the run at the same seq as the phone (compare stream heads).
  8. W and T on the phone return to live; T accepts input.
  9. Faults: kill the phone's socket during step 2's send; on reconnect the intent is resent with the same key and the message exists once (count rows by client_msg_id).

Pass = every step holds on 3 consecutive runs; the stream heads match; no duplicate messages.

# Harness capabilities cmux should own

Research and proposal, 2026-10-02. Docs only; implementation waits for the coordinator's selection. The spec repository was read only. This proposal extends the existing agent, Home, app platform, git, browser and permission owners; it does not create another orchestrator or operation catalog.

cmux should own the continuity of work: context, durable memory, checkpoints, tool configuration and policy. A user should be able to plan with one harness, implement with another, and review with a third without rebuilding the workspace or losing the decisions that matter. Native model reasoning, compaction internals and tool execution stay with each harness unless cmux actually controls their execution boundary.

## What cmux can own

“Own” means cmux can provide the behavior without a special native feature. “Coordinate” means a native capability or adapter is needed for full fidelity. “Enforce” means cmux must mediate the actual effect, not just display a permission prompt. Value is user value; cost includes maintenance across adapters. H/M/L are relative estimates, not measured engineering dates.

### Minimum adapter contract

ACP is a transport and capability negotiation contract, not a guarantee that every agent supports the same tools or enforcement. Its initialization rules say omitted capabilities are unsupported. Its tool-call specification says agents *may* request permission; receiving status updates is not interposition before execution. Prefer advertised `configOptions` to legacy session modes. Do not assume fork, rewind, transcript export, compaction or active-turn steering from basic ACP support alone. [ACP initialization](https://agentclientprotocol.com/protocol/v1/initialization), [permission requests](https://agentclientprotocol.com/protocol/v1/tool-calls#requesting-permission), [configuration options](https://agentclientprotocol.com/protocol/v1/session-config-options).

Every adapter needs a tested capability manifest containing version, transport, start/resume/export/fork support, text/image/resources, skills/MCP roots, commands/models/modes, approval coverage, sandbox coverage, turn ids, cancellation and steering. Distinguish `supported`, `unsupported` and `unverified`. Probe off the UI thread; retain versioned receipts; fail with a typed limitation rather than silently changing behavior.

Shared features must work at three integration levels: structured ACP/native RPC; structured headless CLI plus transcript export; terminal-only launch with explicit context injection and user-directed checkpoints. Terminal-only support can provide files, panes and copied handoff context. It cannot promise reliable turn attribution, true steering or native pre-tool enforcement.

## Build order for the coordinator

This is a recommendation, not a selected implementation queue. Initial interoperability should prove Claude Code to Codex and Codex to Claude Code, then add one native ACP harness. Expand to the rest using capability-tested adapters rather than eight simultaneous integrations.

| --- | --- | --- | --- | --- |

Subagents as panes are the next product slice, implemented through Home's existing orchestration lane. A pane tree, child outcomes and delegated budgets can proceed there while the new work above adds continuity. Existing code-mode and automations lanes continue independently; neither should be rebuilt here.

### 1. Handoff without inventing a shared transcript format

The portable capsule contains task intent; accepted constraints and decisions; outstanding work; current working directory/repository identity; base/head and checkpoint ids; selected file/diff references; verified checks and failures; tool/skill versions; memory revision; and source-session/turn provenance. Keep a bounded summary plus references to raw visible history, not hidden reasoning. Attachments are handles with access grants, not embedded secrets. Summaries must distinguish user instructions from untrusted tool output.

At an acknowledged idle boundary, freeze a revision, create the capsule, start the target harness and send it as explicit context. Persist target acknowledgement and lineage before presenting “Continue in …” as complete. A timeout leaves a recoverable pending operation, not another duplicated prompt. The source stays intact. If a writer cannot be quiesced, hand off into an isolated worktree or refuse a consistent checkpoint. Compaction refreshes the capsule; it does not replace evidence or mutate the old harness's hidden state.

### 2. Checkpoints with a precise undo boundary

Use private snapshot refs/objects or an equivalent repository-host store, not normal history commits. Record HEAD, index, tracked file content/modes/deletions and explicitly selected untracked paths. Respect ignore rules, secret exclusions, symlinks, repository boundaries, large-file quotas and retention. Use an independent temporary index so snapshot creation does not change the user's staging state. Do not pretend one git tree captures submodules, LFS payloads or external databases completely.

Rewind first shows the affected paths and divergence from the selected checkpoint. Quiesce sessions in that working tree; preserve newer edits in a recovery snapshot; restore only the chosen scope. Code state and conversation state are separate: restoring files does not erase a model's memory of later changes. Start a fresh session/capsule, or request a documented native fork/rollback, and state which happened. Network requests, deployments, messages and running external processes are outside git rewind.

### 3. Memory with one canonical owner

Reuse the existing MemoryStore contract and its user/project/team grants. Approved memory entries need source, scope, revision, expiry and an explicit delete path. Render bounded launch-time guidance or a managed include for each harness; use an MCP recall tool for deeper context where supported. Show which revision a session received. Changing canonical memory must not overwrite a user's handwritten instruction file.

Native auto-memory may still be useful, but it is a separate source. Import requires review and provenance. Do not blindly union contradictory `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` and agent-generated notes. Project security instructions keep their existing precedence; memory cannot authorize effects. Sessions can disable memory use and contribution independently.

### 4. Skills and MCP without claiming identical runtimes

Maintain one manifest with origin, pinned version/hash, scope, required tools, supported harnesses and installation receipts. Standard `SKILL.md` is portable instruction packaging; hooks, executable scripts, MCP transport and authentication remain capability-dependent. Offer native skill installs where possible and a labeled explicit prompt/tool bridge elsewhere. Report unsupported capabilities rather than translating them into imaginary native features.

Prefer managed roots/includes or session-scoped config over global edits. Updates preview changes and preserve user-owned entries; removal removes only cmux-owned material. Tool credentials stay in the existing secret store/integration gateway; adapters receive the narrow connection they need. Agent-initiated installs must obey the app platform's existing approval rules. Every install/reload is acknowledged; a running session may need restart and should say so.

### 5. Policy at the effect owner

One editor can normalize principal, repository/host scope, tool/effect class, path/network constraints and `deny | ask | grant`. The evaluator belongs at the catalog/effect owner and acpmux admission path. Native approval settings are projections. Never translate a narrow allow rule into a harness-wide bypass flag. Child sessions and handoffs inherit a narrowed grant, never the source's broader privileges.

Label coverage by session: cmux-mediated operations; verified native approval callbacks; verified host sandbox; or unmediated native tools. ACP alone cannot enforce the last category. Hook timeouts must not create a silent allow path. Official Codex documentation explicitly warns that a pre-tool callback error, timeout or malformed response may fail the hook without blocking execution. Test actual adapters and keep enforcement outside that callback where full coverage is required. [Codex hooks](https://learn.chatgpt.com/docs/hooks).

Universal enforcement requires controlling filesystem, process and network access, including shell grandchildren and inherited credentials. A harness running with broad host access cannot be made uniformly safe by showing it the same policy text. Keep native isolation enabled, apply a verified host/container/VM boundary where available, and report limitations for the rest. This selection needs the existing security owner and coordinator; this docs PR changes no trust policy.

## Ownership, surfaces and validation

Session hosts own processes, repository snapshots and bounded raw session evidence. acpmux owns harness lifecycle, ordered input, permissions it mediates and adapter receipts. The workspace store owns references/lineage and pane layout. Home's memory/orchestration owners own memory and child-run state. Clients own focus, selected panes and transient drafts. Browser/CUA hosts own their effects. Configuration remains with the existing config/app owners. Follow [ownership principles](OWNERSHIP-PRINCIPLES.md), especially single writers, atomic typed operations, idempotency, explicit rejection and refusal of new offline mutations.

Proposed semantic operation families are handoff/capsules, checkpoints, memory projections, tool installations and policy evaluation. Names and schemas must be agreed with the catalog owner before code. Export each selected operation through CLI, MCP where allowed, palette, contextual UI and the mux code-mode API; installations/destructive operations may need explicit surface exemptions. These are proposed families, not current commands. Automation never steals focus; the user action can reveal its resulting pane. Extension access follows the same generated API and grant checks.

Expose defaults in Settings and `cmux.json`: capsule budget/retention and included context, memory use/contribution/scope, checkpoint cadence/paths/size/retention, managed skill roots/versions, policy presets and child concurrency/budget. DEV variants should compare a pane menu, a command-palette action and a handoff review sheet before the coordinator selects UI. Keep events bounded and event-driven with no polling and no new idle work.

Before implementation is called portable, run an adapter conformance matrix covering capability omission, unsupported modes, image rejection, duplicate/uncertain prompt submission, cancellation during handoff, disconnected owners, changed checkout, expired grants, hook failure and restart/reload. Snapshot tests must preserve staging and later human edits. Memory/tool tests must preserve user files and enforce deletion/revocation. Policy tests must attempt native shell/file/network bypasses. Handoff quality needs a task continuation exercise, not just a passing JSON schema.

## Decision requested

Pick the first implementation slice, initial adapter pair and allowed enforcement boundary. Recommendation: handoff first, with a manual repository checkpoint and approved memory references; then automate snapshots. Keep policy coverage visible from the first slice, and reserve a claim of universal enforcement for proven host isolation. No runtime, spec or permission changes are authorized by this research PR.

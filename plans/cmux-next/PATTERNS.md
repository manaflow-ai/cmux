# cmux-next patterns

Status: binding for every change (lead, 2026-10-23). Each pattern has one shared implementation; use it, never a
private copy. A reviewer treats "this case did not use the pattern" as a finding (see
[REVIEW-STANDARD.md](REVIEW-STANDARD.md)). When you land the shared implementation of a pattern, replace "building"
with its file and add its guard. Counts are enforced by the pre-push ratchet (`arch-ratchet.json`, guardrails.py).

| # | Pattern | Rule | Shared implementation | Status / owner |
|---|---|---|---|---|
| P1 | Composition root | Objects with state are built once in the app's composition root (AppServices) and passed in through `init`. No `static shared` with state, no global container, no ambient fallback (`?? .app`). | AppServices + per-domain Host protocols | in progress (cmux-next-arch-targets) |
| P2 | Seam adapter | A C, ObjC, CEF, Ghostty or CFRunLoop callback enters Swift concurrency in one small adapter type; only there may `MainActor.assumeIsolated` appear, with a `// main-proof:` reason. | building | cmux-next-arch-targets |
| P3 | Targeted observation | No app-internal NotificationCenter names. | P4 | Instant create | Every create (terminal, browser tab, pane, column, row, workspace, chat) shows a stand-in in the key's own turn through one intent path with client-minted ids, and reconciles with the daemon's reply by request id; failure rolls back. | DaemonService.intendNow + Intent + ProvisionalPane | New Column/Row and terminals done; browser tabs and the rest in progress |
| P5 | Main-thread budget | The main thread does input dispatch, the small visible-state change and the CA commit only. Socket and CLI requests are parsed on an I/O executor. One priority scheduler: input, then animation and visible updates (one coalesced batch per display frame), then background, each with a frame budget. How work enters it is P15. | CmuxNextWakeups `MainWorkScheduler.swift`, `MainFrameBudget.swift`; contract in [main-thread-budget.md](main-thread-budget.md): building | PL-main |

| P8 | Motion | Default today (F4): per-frame work only for panes whose rect changed; content stays live and is laid out at each frame's size. | P10 | Hidden costs nothing | A hidden thing keeps identity and the bytes to rebuild it; engines, renderers and timers stop. | hibernation (BrowserHibernation) | in progress |

| P10b | Hidden frames | Saved page frames and terminal last frames go into one app-wide LRU with locks for visible frames, a soft limit from physical memory, a 5 min cull and a purge on memory pressure (Chrome `FrameEvictionManager`, rendering-DESIGN R6). | P12 | Benchmarks | GUI benches launch through `scripts/cmux-next/bench_launch.py`, use the STRESS session (`perf-stress-session.py`), report host, macOS and refresh rate, and check that Chromium pages are really Chromium. | P13 | Red then green | A fix lands with a guard that fails on the code before it and passes after, through runtime behavior; commit the guard first. | - | binding |
| P14 | Task traits | Off-main work states its priority (`WorkPriority`, derived from `MainWorkClass`): async work is `work.task(priority) { ... }` (BackgroundWork.task: registered so quit cancels or awaits it by its `ShutdownBehavior`), or a plain `Task { }` that inherits its caller's priority; `Task.detached` and `DispatchQueue.global` only inside CmuxNextWakeups; queues with `qos:` or `target:`; a `Thread` sets `.name` and `.qualityOfService` before `start()` (no `Thread.detachNewThread`); an `OperationQueue` sets `.name` and `.qualityOfService`, and a URLSession gets one as its `delegateQueue:` (never `nil`); never `.userInteractive` outside the closed user-interactive list of [threading-model.md](threading-model.md#closed-user-interactive-list) (main, frame, watchdog and deadline threads, the key echo path and remote view frames; it names its one known exception), never `.unspecified`, `.background` only for work nothing waits for). Every thread, queue and process has a row in threading-model.md with its target QoS and what it waits on (the daemon's in "Daemon threads", process roles in "Process roles" and "Process task roles and spawn QoS"). Work that may block never runs on the cooperative pool: a process wait is awaited with no thread and the spawn runs on the run's own queue (`AsyncProcess`); file I/O, sync system calls and long CPU work run on `BackgroundWork` lanes (`.files`, `.system`, `.cpu`). No synchronous wait on lower-priority work; an awaiting caller boosts it at the call. No later escalation on any macOS (Swift's hook is macOS 26 only and its runtime symbol is strong-linked: a reference stops launch on 14/15), so work a person may wait for starts at that priority. | CmuxNextWakeups `BackgroundWork` (built once in AppServices as `work`; `work.task`, `work.run`), `AsyncProcess`, `OrderedWrites`; consumers so far: the 8 process-wait sites, UpdaterService's kept-versions listing and bundle clone; more in progress. Guard: guardrails rule `task-priority` refuses an added `Task.detached` or `DispatchQueue.global(` outside CmuxNextWakeups, a queue with no `qos:`/`target:` or at a reserved level, a `Thread` with no `.name =` and `.qualityOfService =` on its own variable within 40 lines (a `Thread` subclass: in its body), `Thread.detachNewThread`, an `OperationQueue()` with no `.name =` and `.qualityOfService =` within 10 lines, a thread or operation queue that nothing names, a set level of `.userInteractive`, `.background` or `.default`, and `delegateQueue: nil` (escape `// qos-allow: <why>`); guardrails rule `pool-blocking` refuses a blocking call on a shared pool thread (a detached or child task, a `Task {` off any actor, an actor method, `@concurrent`). | PL-qos (Performance Lead) |
| P15 | Main-thread work is posted with a class | Every main-thread task that is not the synchronous change in the input's own turn is posted with a class (input-response pass, frame, visible, automation, background; userBlocking and idle when p06 tasks 208 and 005 land) and an owner, and records its source location: `mainWork.post(class, owner:)`, `node.queue(class, owner:, on: mainWork).post` for a hideable owner, `work.run(priority, mayBlock:) { }.reply(on: mainWork, class:, owner:)`, a `MainDeadline` for a delay; later `postIdle` (task 005) and `MainDelivery(class:owner:)` (task 217). No `DispatchQueue.main.async`, `Task { @MainActor`, main-inherited `Task {`, `MainActor.run` or `CFRunLoopPerformBlock` in new code. The class comes from the cause: the person's change applies before the commit (input-response pass) or as userBlocking, never behind visible or automation; CLI, MCP and agent work is automation. A view apply is a `VisibleObservation` on its `VisibilityNode`; any other reaction is a `ServiceObservation` (task 026); a hidden node does model work only. Recipes and escapes: [main-thread-budget.md](main-thread-budget.md) section 11 (Chrome: typed task queues, `posted_from`, `TaskSchedulingInBlink.md`). | CmuxNextWakeups `MainWorkScheduler+Post.swift`, `MainTaskQueue.swift`, `VisibilityNode.swift`, `VisibleObservation.swift`, `ObservationCause.swift`, `MainDeadline.swift`, `BackgroundWork.swift`; every type with its file and state: [main-thread-budget.md](main-thread-budget.md) section 12. Guard: `scripts/cmux-next/p06_queue.py --check N` per file group (queues Q1-Q11, QA, with the escapes `main-hop`, `view-observation`, `visibility-walk`, `timer-class`, `raw-observer`, `local-monitor`); the pre-push hook refuses the same six rules on added lines (task 014, landed), with `main-async` for `DispatchQueue.main.async` and `input-monitor` outside CmuxNextInput; task 015 (spec'd) adds the arch-ratchet rows `main_inherited_tasks`, `raw_main_hops`, `unscoped_observations`, `visibility_walks`, `unclassed_main_deadlines`, `local_event_monitors`. | building (PL-main, p06-scheduler) |
| P16 | Input pipeline | Raw `NSEvent`s are seen only in `CmuxApplication.sendEvent`, which hands them to the one `InputEventTap`; an owner subscribes by class, phase and window (core and service packages through `InputObserving` with `InputEventRecord`), and reads the event it answers, never `NSApp.currentEvent`, `NSEvent.modifierFlags` or a `nextEvent(matching:)` loop. Continuous input (moves, drags, scrolls) goes through the window's `FrameInputCoalescer` (a `PointerFrameConsumer`, or `post(kind, owner:)`): the first event of a frame at once, the rest once at the frame tick, a discrete event flushes first; native scroll views, page views and the Chromium host wire opt out with `// input-coalesce: native`. Scroll and pan move layers, not layouts. Prediction (`InputResampler`, intent prewarm, predictive echo) moves pixels only: decisions read real samples, and nothing predicted writes to the daemon or the model. A key does O(1) work before its target (`KeyContextCache`, `KeyRouterMode`). Every tracked input gets one `InputLatencyTracker` slot, closed at its presented frame. Per-event and per-frame paths take no lock, make no allocation or `String` and are marked `// perf-hot:`. How the work an input causes is posted to main is P15 (Chrome: `main_thread_event_queue.h`, `linear_resampling.cc`, `cc/metrics/event_metrics.h`). | `CmuxNextInput/InputEventTap.swift`, `CmuxNextWakeups/FrameInputCoalescer.swift`, `PointerFrameConsumer.swift`, `CmuxNextInputCore/PointerCoalescingQueue.swift`, `InputResampler.swift`, `IntentPrewarm.swift`, `CmuxNextInput/InputLatencyTracker.swift`, `CmuxNextFocusUI/KeyContextCache.swift`; rules I1-I9 and what is not landed: [input-pipeline-DESIGN.md](input-pipeline-DESIGN.md). Guard: guardrail `input-monitor` (pre-push, local only) refuses a new event monitor or raw event-observer closure outside CmuxNextInput; the static queues MQ-monitors and MQ-tracking-loops ([chrome-parity/p04-input.md](chrome-parity/p04-input.md) section 6) read 0 code lines, and MQ-current-event reads 0 code lines outside CmuxNextInput (its one hit is the tap's marked `// current-event: target-action` default in `InputEventTap.swift`). | building (PL-input, p04-input) |

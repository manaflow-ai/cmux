## 2026-10-04 cmux.rd/1 reuse review for the remote tab (lane 17 to the remote tab lead)

Scope: remote-tab.md RT2-RT13 against cmux-rd-proto, cmux-rd-core, cmux-rd-host, cmux-rd-ffi (ABI v1) and CmuxNextRemoteView at d41372ae2ea.

### Reuse as-is
- cmux-rd-proto: 16-byte datagram header, FrameBody (`au_len`, `t_capture_us`, `ref_frame`), Feedback (arrivals, NACKs, acked frame, decode time, need_recovery), InputPacket with sequence numbers, stream carrier framing (type 1 control JSON, type 2 datagram), port 4103, service `remote-desktop`, max_datagram 1152/1332.
- cmux-rd-core: Packetizer and `parity_for`, Reed-Solomon FEC, Reassembler (deadline drop, reference-loss skip, NACK list), FrameGate (one frame in flight, damage coalescing, fps cap; Viz update rects go straight into `FrameGate::damage`), CongestionController (delay gradient, path kinds, relay caps), quality ladder, InputSender/InputApplier (redundancy, exactly once), SessionTable and policy.
- cmux-rd-ffi: the viewer receiver (bytes in; access units, messages and feedback out; one timer). The remote browser client uses it per video stream and links no second copy of reassembly or FEC.
- CmuxNextRemoteView: the `RemoteViewStreamSource` and `RemoteViewInputSink` seams, RemoteDecodePipeline (VideoToolbox, IOSurface NV12), presenters A/B/C, RemoteViewGeometry, HID key map, keyboard policy, path badge.
- cmux-rd-host: only the `H264Encoder` trait and its VideoToolbox, x264 and openh264 backends. X11 capture, XTest injection and the `Control` enum in `wire.rs` are desktop-specific; do not copy them.

### What rd must add (lane 17 owns these)
1. Capability exchange first. Today an unknown datagram kind is refused per datagram and an unknown stream frame type ends the session. So every addition below starts with `caps` in the hello and welcome; a peer sends a new kind only when the other side lists it.
2. Stream multiplexing. The header `stream` field means "display" today, and the rd-ffi receiver ignores it (two video streams into one receiver mix in one Reassembler). Add a `stream.open {stream, kind: video|audio|tiles|popup|up_audio|up_video, codec, layer?}` control message, and a viewer session object in rd-ffi that routes datagrams by stream to one receiver each.
3. Typed control in cmux-rd-proto. The control JSON lives in cmux-rd-host, so a viewer must copy its schema. Move it to cmux-rd-proto with a family field: `rd.*` (hello, welcome, start, stop, stats, keyframe, stream.open) parsed by rd, and extension families (`rb.*` for menus, dialogs, files, clipboard, permissions) that rd routes as opaque bodies to the source's handler.
4. Audio. `DatagramKind::Audio` exists; nothing produces or consumes it. Add Opus packetization (one packet per 10 ms, Opus in-band FEC, no block FEC), a jitter-buffer reducer in rd-core (20 ms target, audio never dropped for video), and `pop_audio` in rd-ffi. Serves remote-desktop.md section 9 too.
5. Upstream media (mic, camera). New kinds `up_audio` and `up_video`. The sender runs CC, so the viewer gets a sender object in rd-ffi (Packetizer, FEC, CongestionController) and the host a receiver; rd-core types are already direction-neutral.
6. Timing for input-to-paint and RT12. InputPacket gets `t_viewer_us`; FrameBody gets an optional extension with `input_seq_applied` and host stage stamps (begin-frame, capture, encode done, send). The viewer adds complete, decoded and presented. Feedback gains `last_presented_frame`, `presented_us` and the display refresh and vsync phase (section 6.1 lists them; they are not built). The begin-frame source reads the vsync phase from feedback.
7. Multi-viewer. SessionTable has one viewer per session and the host encodes per session. Add a source with N subscribers: one encoder per (source, size), per-viewer Packetizer, FEC, CC and NACK history, encoder target = minimum of the viewers' targets. The smallest-viewer size rule (U6) belongs to the source, not to rd.
8. Multi-source per session. One link, one session principal, several sources (a display, a tab, its popup surfaces, per-layer streams for r9). Policy runs once per session; each source adds its own hook (a remote tab uses the browser site permission and the automation lease, not desktop consent RD7).
9. Media passthrough (RT13) needs only `codec` in `stream.open` and a presentation timestamp in place of `t_capture_us`; nothing else changes.

### API seams so cmux-remote-browser does not duplicate transport, CC, FEC, decode or present
- Host: a new crate `cmux-rd-engine` (MIT, no X11, no x264) split from cmux-rd-host. It owns sessions and policy, stream ids, packetize, FEC, pacing, CC, NACK history, feedback, input apply and the control router. A source implements one trait: damage in, `encode(target_bps, size) -> access unit`, `on_input(event)`, `on_extension(family, body)`. cmux-rd-host becomes the desktop source; cmux-remote-browser becomes the Viz source.
- Transport: one adapter (lane 17) on the landed `cmux wg hub --control` socket (`datagram.bind` port 4103 class media, `path.subscribe`), with the stream carrier as fallback. Both apps use it.
- Viewer: rd-ffi gains `cmux_rd_session_*` (stream routing, input sender, upstream sender); the receiver stays per stream. CmuxNextRemoteView exports its decode and present stack as one component (`RemoteVideoSurface`) that CmuxNextRemoteBrowser embeds; the browser view owns only input, native UI and popup panels.

### Conflicts that need a decision
- D-RT-RD1: remote-tab.md section 3 decodes in Rust (objc2 VideoToolbox) with Swift setting layer contents; CmuxNextRemoteView decodes in Swift today (tested). Two decode paths is the duplication to avoid. Recommendation: Swift decode and present for stage 1; the r9 compositor (Rust, Metal) can take decode later for both apps at once.
- D-RT-RD2: cmux-rd-host is GPL-3.0-or-later (x264 default). cmux-remote-browser links only the MIT crates (proto, core, engine) and gets x264 through a feature or a separate process; the license lane decides.

Ownership: lane 17 builds items 1-8 and cmux-rd-engine; the remote tab lead owns `rb.*`, the Viz source, popup surfaces and the split compositor. Lane 17 reviews r2.

## 2026-10-05 Lane 17 decisions on rd changes C1-C8 (remote-tab-protocol.md section 7)

Map to the 2026-10-04 review items (R1-R9). Every new kind, tag and frame type waits for C1: an older peer refuses unknown kinds, and an older host that cannot decode an input tag drops the whole packet and never acks it.
- C1 `hello.service` (R1): accept, adjusted. Port decided (REMOTE-TAB-R1 Q5, coordinator 2026-10-05): remote-browser uses the same overlay port 4103 as remote desktop, so one rd session and one congestion controller serve each peer pair. The host routes each session by the hello `service` (default `"desktop"`; `"rb/1"` for the remote browser) and refuses an unknown service with `refused {reason: "service"}`. Hello also carries `caps` (list of rd features: `input.service`, `tile`, `up_media`, `bulk`, `stream.open`, `clock`); welcome echoes the service and the accepted caps; a peer uses a feature only when both list it. Policy separation between "view my browser" and "control my desktop" comes from the per-service grant check in the host, not from the port.
- C2 service input tag 0x80 (R3): accept, adjusted. Layout `u8 0x80`, `u8 flags`, `u16 len`, bytes; flag bit 0 `must_deliver` gives the release rule (repeat until acked), because a key-up inside opaque rb bytes would otherwise be dropped after three sends and stick a key. Bound: `MAX_PACKET_PAYLOAD` (1136) minus 9 bytes, not `max_datagram`.
- C3 `Tile` kind (new): accept, adjusted. Tiles ride their own rd stream id (opened with `stream.open {kind: tiles, of: <surface stream>}`), not the video stream, because the reassembler numbers frames per stream and tile and video frame numbers would collide; `ref_frame` names the video frame the tile applies on top of. Same packetizer, FEC and reassembly.
- C4 viewer-to-host media (R5): accept. Kinds `UpAudio` and `UpVideo`; the viewer runs Packetizer, FEC and CongestionController through a new rd-ffi sender, the host runs a Reassembler and sends Feedback back.
- C5 `bulk` stream frame type 3 (new): accept, adjusted. Bulk frames at most 64 KiB (not the 1 MiB stream frame limit) so control waits at most one bulk frame; credit-based flow control (`rd.bulk.credit {transfer, offset}` from the receiver) so an upload cannot fill the carrier; the one-frame-per-media-interval rule lives in the engine scheduler. On the stream carrier bulk shares one TCP stream with media, so the engine pauses bulk while a frame waits.
- C6 per-stream feedback and recovery (R2): accept. The datagram header `stream` field already names the stream; the viewer gets a session object in rd-ffi that routes datagrams by stream to one receiver each (today one receiver mixes every stream), and the host keeps recovery state per stream.
- C7 shared crates (R3 seam, engine split): accept, adjusted. Typed control (`hello`, `welcome`, `start`, `stop`, `stats`, `stream.open`, `bulk.credit`) goes into cmux-rd-proto behind a `serde` feature, not a separate carrier crate; the carrier I/O and session driver become `cmux-rd-engine` (MIT, no X11); encoders become `cmux-encode` with VideoToolbox and openh264 only. x264 stays in the cmux-rd-host binary (GPL; coordinator D-RT-RD2). Needs a cmux-tui window (new crates, Cargo.toml and Cargo.lock).
- C8 clock offset (new, R6 is related): accept. rd-core gets a clock-offset estimator from timestamped feedback (viewer `t_viewer_us` out, host echo and `t_host_us` back; minimum-RTT filter); the engine exposes `offset_us` and `rtt_us` to services, and rd-ffi exposes them to the viewer.
Still lane 17 and not in C1-C8: R4 audio, R6 input and stage timestamps, R7 multi-viewer, R8 multi-source.
Order: C1 -> C6 -> C2 -> C8 -> C3 -> C5 -> C4; C7 when the coordinator grants a window (the remote tab lead's r2 needs it before it copies the carrier).
Coordinator decisions recorded: D-RT-RD1 Swift VideoToolbox decode for stage 1 (Rust objc2 later, after a measurement); D-RT-RD2 cmux-remote-browser links only MIT/Apache crates, x264 stays in the host binary.

# cmux-next code mode

Status: first slice implemented on 2026-10-02 in PR branch `feat-cmux-next-code-mode`, based on `feat-cmux-next`. This proposal is for the coordinator and links to [automations-runtime.md](automations-runtime.md), which should consume the same generated SDK and permission catalog.

## Agent chats: code mode is the default MCP surface (2026-10-19)

`cmux mcp serve`, the server acpmux gives every local agent chat, lists two
tools: `cmux_docs` and `cmux_exec` (`cmux-tui/crates/cmux-tui/src/cli/mcp/code_mode.rs`).
Before this, it listed one tool per operation: 638 tools, 459 of them app
actions, 834 KB of schemas (about 208k tokens in every agent turn). A one-word
ACP Claude turn read 318k cached tokens, compared with 42k for interactive Claude.

- `cmux_docs` searches the full tool list (daemon operations, browser host,
  agents, keybindings, render, window list, app actions) and returns schemas.
- `cmux_exec` runs a JavaScript async function body in an embedded QuickJS
  engine inside the `cmux` binary. Its only host functions are `cmux.call`,
  `cmux.docs` and `console`; there is no file system, network, process or
  timer access. Every call goes through the same `Server::call` path as a
  direct tool call, so a script has exactly the rights of the tools.
  Limits: 64 MiB heap, 2,000 calls, 30 s of computation without a call.
- `cmux mcp serve --all-tools` keeps the old one-tool-per-operation list.
- Per harness (Lawrence 2026-10-19, `acpmux agent_tools::lists_all_tools`): a
  harness with its own tool search gets `--all-tools` and loads the tools a
  turn needs; every other harness gets code mode. Claude Code (every profile,
  with `ENABLE_TOOL_SEARCH=true`, which acpmux sets because Claude Code turns
  tool search off by itself behind our routers) and Codex have it. Measured,
  one-word turn with 641 cmux tools: Claude Code 34,384 prompt tokens with
  tool search and 314,542 without; Codex 20,244, the same as with code mode.
  OpenCode 1.19 has no tool search for MCP tools and gets code mode. pi-acp
  passes no `mcpServers` to Pi, so Pi has no cmux MCP tools in either mode.
- The bun runner (`cmux run`, `cmux-code-mode-mcp`) below stays for TypeScript
  scripts against the typed SDK; agent chats no longer need bun.
- Not yet in code mode: the separate `cmux-cua`, `cmux-secrets`,
  `cmux-sessions` and offer MCP servers that acpmux also injects.

## Inventory

The cmux-tui resource catalog at `cmux-tui/spec/resource-operations-v2.json` is the current wire source of truth. On `feat-cmux-next` it contains 127 operations and is 330,205 bytes, about 73,715 cl100k tokens when serialized as checked in. `sdk-schema.json` is 392,755 bytes, about 108,734 cl100k tokens. The catalog is already used by protocol validation, CLI coverage tests, and generated bindings. The checked-in TypeScript SDK is typed, has a Node transport and a browser transport, and has no runtime dependency in its browser-safe entry.

The current CLI exposes noun-first areas for machine, session, client, workspace, screen, pane, tab, terminal, browser, notification, agent, sidebar, pairing, projection, provider and raw. `cmux help <topic>` is local and static today. The resource CLI parser is checked against 120 catalog paths. Tasks have a second, narrower catalog that already declares CLI, MCP, palette and `code_mode` surfaces and exports TypeScript declarations.

Agent discovery is split by harness. The bundled `cmux-cua` MCP server is injected automatically into Claude Code and Codex sessions only. Codex receives ten CUA tools (`list_apps`, `get_app_state`, `click`, `perform_secondary_action`, `set_value`, `select_text`, `scroll`, `drag`, `press_key`, `type_text`); Claude receives the broader native cmux CUA contract. Other harnesses do not receive the injected MCP server. Skills are checked in under `skills/cmux-*`; the existing CUA skill is 18,094 characters, about 4,121 cl100k tokens. The actual bundled CUA JSON schemas are generated by the pinned helper and are not checked into this repository, so a live per-session schema token total remains unverified and must be captured from `tools/list` for each harness before the execute slice is evaluated.

## First slice: progressive disclosure

The prototype adds a local `cmux docs search <query>` command to cmux-tui. It searches operation names and catalog JSON for all query terms and returns up to 20 matches with operation class, target, parameter names and result type. `--json` and `--quiet` remain local and do not require a running session.

`cmux help <area>` now appends a catalog-generated operation index for that area and points to `cmux docs search` for parameter details. The index is derived from the same catalog used for validation, so new operations appear without a second help table. `skills/cmux-code-mode/SKILL.md` teaches any harness to call help, search only the relevant operation details, and then use the normal CLI.

The first slice intentionally does not add an MCP server or a second SDK. It measures discovery cost and gives non-Claude/non-Codex harnesses a documented path immediately.

## Execute slice

The execute prototype in the follow-up branch exposes the existing generated TypeScript client through one runtime entry point:

- `cmux run <script.ts>` dispatches through `cmux-code-mode-runner`. The prototype runs Bun in a Linux `bwrap` namespace with no host network, no host home, read-only runtime and source mounts, a tmpfs for transient writes, and one explicitly bound cmux Unix socket. It fails closed when bwrap is unavailable; a macOS sandbox profile is a follow-up before shipping the command in the app bundle.
- The MCP surface is exactly `cmux_docs` and `cmux_exec`; docs returns catalog excerpts, and exec writes a bounded temporary script then invokes the same sandbox runner. Both paths use the generated TypeScript Node client and the same authenticated socket.
- The runtime has no ambient host filesystem or network capability. Every operation still passes the catalog's existing class, selector and mutation gating. The CLI and MCP paths share the runner and permission boundary.
- Prefer the existing generated TypeScript SDK as the only public API. Regenerate its operation methods and declarations from the catalog rather than hand-writing a second client. The SDK and catalog permission contract are shared with `automations-runtime.md`; the interactive `cmux run` executor may use the same pinned workerd runtime or a smaller QuickJS host only if that host implements the exact same capability boundary and reviewable policy.

A first runtime prototype should prefer the pinned workerd path already being evaluated by `automations-runtime.md`; use QuickJS only if the existing build and embedding path can keep the binary and policy surface smaller while preserving TypeScript support. Do not allow ambient `fs`, `net`, child processes or dynamic imports.

## Catalog extension proposal: cloud and CUA

The execute slice keeps one `cmux.protocol/2` socket and one typed resource
catalog. Cloud and CUA must join that path through owner relays; adding names
to the JSON catalog alone would make discovery disagree with the Rust enum,
router, result validation and server dispatch.

Cloud already has a separate generated catalog at
`backend/catalog/cloud-operations.json` and a typed client under
`backend/packages/protocol`. The cloud follow-up should add a host-owned
broker that obtains credentials outside the sandbox, translates the merged
catalog envelope to the cloud wire protocol, and returns typed results. The
broker should first cover the cataloged cloud control-plane reads and
mutations. Cloud VM lifecycle operations such as pause and resume need their
own catalog entries and owner decision because the current `/api/vm` client is
outside that catalog.

CUA remains a later relay. The CUA host owns its authenticated socket and
session credentials. The cmux-tui resource service should route typed `cua.*`
operations to that owner before code mode exposes them. Candidate groups are
session start/end and reads, timeline/frame reads, and the existing act/observe
families. User-only stop, pause, resume and policy operations stay excluded
from agent code mode unless the owner grants them explicitly.

Until those relays land, `cmux run` and `cmux_exec` expose only the embedded
cmux-tui catalog. A script must not open a second cloud or CUA socket, and the
sandbox must not receive cloud bearer tokens or CUA launch credentials.

## Measurement

Capture a live `tools/list` payload for every supported harness and count it with the same tokenizer used for the model under test. Compare:

- current MCP schemas loaded at session start;
- the short code-mode skill plus one `cmux docs search` result;
- the two-tool MCP profile (`cmux_docs`, `cmux_exec`) plus one script;
- turns, wall time, success and failure recovery.

Use these tasks: open a PR diff in a split and run its tests; screenshot a browser tab and summarize it; pause idle cloud machines; and one mixed task that creates a pane, runs a command and reads its result. Record the exact script and catalog revision with each run.

## Automations link

`automations-runtime.md` is the owner of chief-written code execution and its sandbox policy. Code mode must reuse its SDK, runtime and capability checks. The automation `code` body type should call the same `cmux_exec` contract, with a chief-authored origin and the same catalog permission gates. Do not fork a second automation-only client or grant scripts broader rights than the CLI.

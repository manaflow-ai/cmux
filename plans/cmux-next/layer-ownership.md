# Layer ownership: Rust, Swift, TypeScript (binding)

Status: chief decision 2026-10-09, after Lawrence: "we need to ensure proper ownership between swift/rust/typescript in general." Written by the ownership-audit lane at tip 01d62a862598.

This file answers one question: which LANGUAGE LAYER owns a piece of state or a rule. OWNERSHIP-PRINCIPLES.md (binding) and ownership.md answer which ROLE owns an entity (session host, workspace store, client) and how ops, echoes and intents work. ownership-v2.md has the process map and the per-actor owner table. home-state-ownership.md covers Home. This file does not repeat them; when it disagrees with OWNERSHIP-PRINCIPLES.md, that file wins until the chief changes it.

## 1. The model

1. The Rust daemon owns all durable state, all shared state and all product rules. "Daemon" means cmux-tui-core and its peer actors in the same process (store, session host, home, config, git/files), plus acpmux for agent sessions until it moves in-process (cx-ncc.27). Each piece of state has exactly one writer. The daemon exposes it as v2 resource operations (cmux-tui/spec/resource-operations-v2.json) and event streams.
2. The Swift app owns presentation and platform: windows, views, focus, input, gestures, animation, and macOS services (Keychain custody, notifications, TCC prompts, NSWorkspace, pasteboard, Chromium runtime). It keeps a read-only mirror of daemon state and sends intents. The only optimistic layer is a pending-edit log that clears when the daemon confirms or rejects (the SidebarPendingEdits pattern, cx-odqn, `Packages/macOS/CmuxNext/Sources/CmuxNextSidebar/Logic/SidebarPendingEdits.swift`).
3. TypeScript and React webviews are views. Data comes through a generated typed API (webviews/src/protocol/generated, the generated page clients, acpmux generated types). A webview holds only local UI state (hover, open or closed, the text in an input, scroll). It holds no business rule and no durable product state (no localStorage or IndexedDB copy of product data).
4. A rule needed in more than one layer (validation limits, policies, catalogs, enums, op names, wire types) lives once, in Rust or in one data file, and reaches Swift and TypeScript by codegen with a CI drift check. Never by a hand copy, and never by a "parity test" that keeps two hand copies equal.
5. Mobile follows the same model through the shared Rust core over uniffi (mobile-rust-core.md, MOBILE-RUST-1 to 5). Swift on iOS and Kotlin on Android hold UI and platform only.

Exceptions that stay (recorded decisions, not violations):
- The cloud owners are TypeScript Durable Objects (ConversationDO, UserDO, FeedDO, TeamDO, MuxDO). The daemon holds a replica and never decides a cloud op. The Rust and TS conversation reducers are both kept equal by the conformance corpus (ownership-v2.md 1a item 4, D-H2).
- Personal client view state (focus, selection, window frames, sidebar width, per-window selected tab) is owned by the client install; when other tools must read it, the client publishes it to its own single-writer record in the store (OWNERSHIP-PRINCIPLES.md "Single writer per entity").
- Browser runtime belongs to the Mac app that renders the page; the store owns the tab record.
- Key custody: private keys stay in Keychain or the Secure Enclave; Rust asks a platform Signer to sign (mobile-rust-core.md 3). Holding the key in Swift is platform work, not state ownership. Deciding WHICH principal signs is a rule and belongs in Rust.

## 3. Rules

- L1. Name the owner layer before writing code. Durable, shared or rule-bearing state is Rust. If you think it must live in Swift or TS, write the reason in this file's table first.
- L2. One writer per state. A second writer is a bug even when it "only repairs" or "only caches"; a cache is a read-only mirror that the owner's events refresh.
- L3. Swift and TS never decide a product outcome the daemon also decides (close a workspace, accept a folder, pick a status, answer a permission). They render the daemon's decision, including its typed reject.
- L4. The only optimistic state is a pending-edit log keyed by an idempotency key, cleared on echo or reject. To compute the optimistic view, call the Rust reducer (FFI, as RustSidebarClient does with `cmux-layout-reducer-ffi`) instead of a Swift copy of the reducer. A Swift copy is allowed only behind a property test against the Rust reducer, and only until the FFI path exists.
- L5. Shared constants, catalogs and enums live once in Rust or one data file and are generated into Swift and TS. Every generated copy has a `--check` mode run by safe-push or CI. A parity test between two hand copies is a migration aid, not a fix.
- L6. Op names and wire types reach Swift and TS by codegen from resource-operations-v2.json (TS and the 7 SDKs already have emitters; Swift has none yet, see V-1).
- L7. Webviews keep no durable state and open no side channel to an owner that bypasses the generated API, unless the channel is the designed transport and its client is generated.
- L8. A new mobile feature with a wire contract goes into the Rust mobile core, never into a Swift package that Android would have to copy.
- L9. Review subagents cite these rule ids together with code-quality.md G1 and SW11.

## 4. How to add new state (checklist)

1. Is it per-view and never needed by another process or after a restart (hover, drag, scroll, input text)? Keep it local in the view (Swift or TS). Stop here.
2. Is it client view state that another tool must read (selected workspace per window, frame)? The client install owns it and writes only its own record in the store. Name the record.
3. Otherwise it is daemon state. Pick the actor (session host, store, home, config, acp, git/files, sync) from ownership-v2.md 2.3 and name the single writer.
4. Define the op family in resource-operations-v2.json (or the actor's catalog), with idempotency key, reject codes and events. Write the pure reducer with invariant tests (RS9).
5. Generate the Swift and TS types. Do not hand-write the wire struct.
6. Swift: mirror it read-only, send intents, add a pending-edit entry only if the user needs to see the change before the echo; compute the optimistic view with the Rust reducer.
7. Does any rule (limit, enum, list, default) apply in more than one layer? Put it in Rust or one data file and generate it; add the `--check` step.
8. Mobile needs it? It goes into cmux-mobile-core and reaches iOS and Android through uniffi.
9. Add the row to section 2 of this file in the same commit, and a COORDINATION.md line if the protocol changed.

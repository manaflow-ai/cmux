# cmux next: remote tab step r1 (remote presentation in the CEF fork) and the r2 crate

Status: technical design, 2026-10-04, remote tab lead (worktree nx-remote-tab). Parent: remote-tab.md (RT1-RT14, spec/remote-tab.md, decision REMOTE-TAB). Wire protocol: remote-tab-protocol.md (`cmux.rb/1`). Reused: remote-desktop.md (RD1-RD11, `cmux-rd-*` crates), transport.md, browser-host.md, OWNERSHIP-PRINCIPLES.md, the CEF fork notes (`cef/CMUX.md` in manaflow-ai/cef, `.cmux-scratch/nx-worker/cef-build-facts.md`), cef-cmux18-candidates.md.

Source base for every citation: Chromium 154.0.8037.58 and CEF branch 8037 as checked out at `~/fun/cef-cmux-build/chromium/src` (fork commit 8f931f2, `CMUX_CEF_API_VERSION` 15 in that tree). Line numbers are from that tree. "VERIFIED" means I read the code there. "UNVERIFIED" means a belief that a fork test must prove before the patch depends on it.

## 0. Result in one paragraph

Chromium already has every large part we need. Chrome's own "new headless" mode keeps full Chrome (views, Browser, extensions) running with windows that never reach a screen: on macOS through `ScreenMacHeadless` and headless `NativeWidgetMacNSWindow`s, on Linux through the Ozone `headless` platform. CEF's Alloy off-screen path already turns a `viz::FrameSinkVideoCapturer` into IOSurface or CPU frames with damage rects (`CefVideoConsumerOSR`). CEF's Chrome style already routes context menus, JS dialogs, file choosers, downloads, permission prompts and cursor changes to client handlers. What does not exist: a switch that gives Chrome style the headless platform without the rest of Chrome's headless mode, a frame export for Chrome style (every paint, resize, IME and begin-frame method of `ChromeBrowserHostImpl` is `NOTIMPLEMENTED()`), data-model routing for `<select>` and page popups, and key routing that keeps Chrome's accelerators off the server. The r1 patch set adds the first two (RP1, RP2) and the begin-frame source (RP3, can slip to r2); the others are designed here and land in r3 and r4.

## 2. Shape of r1

```
remote browser host process (Rust main, cmux-remote-browser-host)       one per (host, profile)
  main thread: CEF UI loop (CefRunMessageLoop through the shim C ABI)
    libcmux_rb_shim (C++, CEFShim style)  ── cef_cmux.h cmux_rp_* ──▶ CEF fork (Chrome style, --cmux-remote-presentation)
      per remote tab: one headless CefWindow + CefBrowserView (one Chromium Browser, one tab)
        RP2 capture of the tab's RenderWidgetHostView frame sink ─▶ frame lease (IOSurfaceRef | shm ptr, damage, counter, t)
  encoder thread(s): frame lease ─▶ VideoToolbox / x264 (r2) ─▶ cmux-rd-core packetize + FEC + CC ─▶ rd carrier
  r1 only: frame lease ─▶ PNG writer (loopback, fork test harness)
```

- One Chromium Browser per remote tab, not one Browser with many tabs (`--cmux-tabbed-windows` stays for the local app). Reason: Chrome renders only the active tab of a Browser, and capture of an inactive tab's frame sink depends on viz servicing copy requests on an undrawn surface (UNVERIFIED, so not relied on). Cost: `chrome.windows` shows one window per remote tab. Extensions that group tabs per window see that shape; the cmux layout is still the user's real arrangement (RT11).
- The CEF browser process is the Rust host binary (in-process shim, as the local app links the shim). IOSurfaces and shared memory never cross a process boundary before the encoder. The CEF helper processes stay CEF's own helper binary.
- The page's device scale and size equal the viewer pane's backing scale and size (RD2, RT4): the shim sets the headless display (F9) to the viewer's screen and the window to the pane size in DIP; the capturer resolution is fixed to the pane's pixel size, so the encoder never scales.
- Idle = 0: no damage, no capture (F4), no encode, no packet. With RP3 the begin-frame source also stops when nothing needs frames.

## 4. Capture details (RP2)

- Format and buffers in r1: ARGB everywhere. macOS: `kPreferMappableSharedImage` → BGRA IOSurface (F3, F5); VideoToolbox in r2 takes a `CVPixelBuffer` made with `CVPixelBufferCreateWithIOSurface` and converts to YUV in hardware. Linux without GPU: `kDefault` → read-only shared memory, mapped once per pool buffer. The bench (r2) decides between ARGB+hardware conversion and NV12 from the capturer on macOS; NV12 cannot be switched on during a capture (F4), so the choice is per session.
- Linux CPU path for x264: a second capturer is not needed for video in r1. In r2 the plan is I420 from the capturer for video (no conversion in our code) and a short-lived second ARGB capturer only for the lossless top-off after motion stops (one `RequestRefreshFrame`, then stop). This keeps the steady state at one copy.
- The copy is a GPU blit from the compositor's render pass into the pool buffer on macOS (no CPU copy); on Linux software compositing it is one CPU readback. "Zero copy" in remote-tab.md means no CPU copy on macOS.
- Damage: forward `capture_update_rect` with `capture_counter`. The consumer treats a missing rect, a counter gap, a size change or a refresh as full damage (the rule in F3). The rect is one union (F4); finer regions for tiles are an r2 question (count the damage quads in the fork only if the bench shows the union rect wastes tile bandwidth).
- Pool pressure: the shim releases a lease when the encoder has consumed the surface (VideoToolbox's output callback, or x264's encode return). The encoder keeps at most 2 leases; a third arriving frame replaces the queued one (newest wins, RD5).
- Timing: `SetMinCapturePeriod` = the viewer's frame interval (from `rb.vsync`), auto throttling off, animation lock-in off, min size change period 0 (the CEF settings, F3). With RP3 the begin frames, not the oracle, set the pace.
- Color: the capturer tags ARGB frames as sRGB (`frame_sink_video_capturer_impl.cc:112-130`). Viewer screens are usually Display P3. r2 tags the encoded stream and the client color-manages; whether the page should render in the viewer's color space (HDR, P3 content) is open question Q3.
- Visibility: a headless widget reports visible (F7), so only `IncrementCapturerCount` decides background throttling. Pause (no visible viewer) releases it and stops the capturer: CPU at rest is the cost of a background tab.

## 5. Fork tests

The fork has an embedder harness for the local app (`tests/cmux_embedder`, macOS, needs a GUI login session). r1 adds `tests/cmux_remote/`, a separate small harness that starts CEF with `--cmux-remote-presentation` and drives `cmux_rp_*`. It writes every captured frame as PNG into an artifact dir (the loopback viewer of step r1). It runs on the fork build host cmux-lawrence-2 for macOS (no window may appear; the test proves it) and, when the Linux fork artifact exists, on a Linux Testbox with no `DISPLAY` and no `WAYLAND_DISPLAY`.

## 6. Build and release path

- Branch `cmux/8037-remote` in manaflow-ai/cef off `cmux/8037-ext`; PR into `cmux/8037-ext` after the CEF crash lead reviews it. It rides cmux.18 or later (cmux.17 is the DCHECK-only build now running on cmux-lawrence-2).
- macOS: `scripts/build-cmux-cef.sh build` on the warm tree `~/cef-build` of cmux-lawrence-2, which needs a fork build slot from the coordinator. RP1 touches `ui/display/mac` and RP3 touches `ui/compositor`, so expect a larger rebuild than the 15-30 min libcef-only case (not measured).
- Linux: blocked. No Linux fork artifact exists; lane 19 backlog (a) waits for the cost and disk approval of a Linux build host (Testbox ≥250 GB, 3-5 h first build). r1 on Linux starts when that exists. RP6 changes a GN arg for Linux, so it needs a full Linux build.
- The remote build is the same artifact as the local one (the switch selects the mode), except RP6's Linux GN arg. If RP6 stays Linux-only and compiles, one Linux artifact serves both.

| `cmux-tui/crates/cmux-remote-browser-host` | binary, own workspace (excluded like `cmux-rd-host`, so CEF and encoder deps never enter the cmux-tui Cargo.lock) | CEF main loop through `libcmux_rb_shim`, session owner, encoders, rd carrier, browser host role `remote` for `cmux host run` | no (fleet and Testbox runs) |
| `libcmux_rb_shim` | C++ in the CEFShim style (`Packages/macOS/CmuxNext/CEFShim`) with a Linux build | CEF handlers → C callbacks; `cmux_rp_*` calls; JSON for menu models (reuses `MenuItems` from `shim_client.mm`) | its pure helpers get C++ unit tests like `CEFShim/tests` |

Reuse, not duplication (umbrella instruction 2026-10-04): packetizing, FEC, reassembly, NACK, flow control, congestion control, the quality ladder and input delivery come from `cmux-rd-core`; the datagram header, frame body and stream framing from `cmux-rd-proto`; the viewer's reassembly and feedback from `cmux-rd-ffi`; decode and presentation from `CmuxNextRemoteView`. The rd changes rb needs are listed in remote-tab-protocol.md section 7 for the lane 17 lead.

Client side (r2, Swift thin): `CmuxNextRemoteBrowser` is the pane view (NSTextInputClient, events, NSMenu, NSCursor, sheets) and links the rb reducers through the client FFI (Q4). Swift holds no protocol state.

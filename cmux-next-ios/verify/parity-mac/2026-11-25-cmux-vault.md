# cmux vault: end-to-end encrypted secrets and env for Cloud (Settings > Cloud > Vault, `cmux vault`, MCP `vault_*`, `cloud.vault.enabled` default off)

- Section: Cloud
- Mac sends: nothing over the link; each device calls cmux Cloud's `/v1/cloud/vault` routes with the person's own sign-in (cmuxterm-hq docs/design/e2e-vault.md, cmux#56890)
- Phone: Settings > Cloud > **Vault**: off with **Turn On**; waiting with this iPhone's 8-digit code to approve from another device; on: the kept names with values masked `••••••••` and their scope, **Add Secret** / Edit (a secure field; the old value is never shown) / Remove, **Import from .env…** (Files picker, a checkbox per name, a scope), Devices with **Approve…** after comparing codes and Remove (rotates the key)
- State: partial
- Notes: cmux#56920. Limit: not yet run against a live `/v1/cloud/vault` backend (cmux-platform routes); Rust tests run the whole path against an in-memory server. All crypto, `.env` parsing and planning is Rust (`cmux-vault-e2e` through `cmux-mobile-link-ffi` `vault.rs`); Swift sends only `/v1/cloud/vault` requests (`AccountCloud.vault`) and keeps this phone's device key in the Keychain (`cmux-vault-device`, this device only, after first unlock). The phone seals each machine's values to its daemon key after it starts, makes or restores a Cloud machine, after a change, and on launch and foreground (one sync at a time, 60 s budget, off the main thread), so a machine started from the phone while the Mac is off still gets its secrets. No value is shown, logged or kept outside the Keychain. No link service or Mac trust policy changes (SECURITY.md covers the link only).

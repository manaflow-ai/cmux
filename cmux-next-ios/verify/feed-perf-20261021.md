# Feed scrolling under pressure: verification

Branch `feat-cmux-next-ios-feed-perf`, 2026-10-21 and 2026-10-22. Report: "Feed scrolling
still feels unsmooth and hitchy" on an iPhone 16 Plus, with two Macs and many Codex and
Claude events.

## Rig

`verify/feedperf/rig.sh` builds the Demo configuration (optimized, DEBUG developer surface)
for the simulator on mini-cmux11s. It runs the app on its own iPhone 16 Plus simulator
(iOS 26.5) on mini-cmux15, the quietest cmux mini. Simulator.app was never opened, and
nothing ran on the laptop.

Pressure (`FeedStress.swift`):

- `CMUX_MOBILE_FEED_STRESS=320`: 320 events, cycling through 8 kinds. Markdown answers have
  diffs, code blocks, tables and lists. There are finished and failed cards, terminal asks,
  and permission cards with a 4-line shell command in a code card. There are questions with
  options, and quote bubbles from you and from the agent. Events come from two Macs and two
  agents, and some carry replies.
- `CMUX_MOBILE_FEED_STRESS_LIVE=4`: 4 live changes a second while it scrolls: a new event
  at the top, as live mode adds one, a re-merged event with changed text, a read, and a
  no-op merge. The tab bar badge follows `needsYouCount`.
- `CMUX_MOBILE_FEED_AUTOSCROLL=1`: the Feed's UIScrollView is scrolled to the bottom and back
  at 2400 pt/s (a fling-speed drag), one frame-interval window per direction.

Each window logs frame intervals (`FrameIntervalLog`) and, new here, the main thread's CPU
time per frame (`mainThreadCPUPerFrameMs`, from `thread_info`). A simulator's frame times
swing with the host's load. Main-thread CPU per frame says whether a late frame was the
app's own work. `summarize.py` prints the p99 and max frame time, hitches (frames over
1.5 intervals), dropped frames, hitch time ratio (ms/s), and `main_busy_frames` (frames whose
main thread used more than one frame's budget). The simulator's display runs at 60 Hz, so a
frame is 16.67 ms.

Instruments: `xctrace` could not record on the cmux minis over SSH. Developer Mode is off
there (`DevToolsSecurity -status`), so attach waits for an authorization prompt that SSH
cannot answer. The cmux user has no passwordless sudo. On aws-m4pro-6, which has Developer
Mode on, the attach did start, but the trace stayed empty and the host stopped answering
Tailscale SSH. The profiles here come from `sample` at 1 ms over the whole autoscroll
(`rig.sh trace LABEL sample`), parsed by `verify/feedperf/sample_main.py` (main-thread
inclusive time by frame). The Animation Hitches template does not run on the simulator
anyway (verify/chat-feed.md). No Animation Hitches, Time Profiler or SwiftUI-template
trace from a cmux mini is part of this record.

## What was slow, with stacks

Base: origin/feat-cmux-next `1f4437e6f083` plus the rig commit `6695760a410c`. Without live
traffic, the base Feed scrolled at **57–64 ms/s** of hitches, with p99 at 36 ms and a max of
45–57 ms. Under live traffic it was 41–66 ms/s, and the idle window (nothing moving, 4
changes a second) reached 24–45 ms/s.

1. **The cost of a row that scrolls in, not the web views.** Per-frame CPU shows a busy
   frame (10–20 ms of main-thread work) every 8–11 frames, one for each row of about 400 pt
   coming into view at 40 pt a frame. Removing parts one at a time showed this:
   - Every row with only the avatar and an empty column: 0 ms/s.
   - Plain `Text` rows: 0 ms/s, the same 320 events.
   - Replacing the web bodies with grey boxes: no change (63 ms/s). Web views were not the
     main cost.

   In the 1 ms sample the time sat in
   `LazyHVStack.lengthAndSpacing` → `_PaddingLayout.sizeThatFits` →
   `StackLayout.UnmanagedImplementation.sizeChildrenIdeally` / `placeChildren` /
   `prioritize`. That is the cell's `HStack` and `VStack` measuring each part several times
   (ideal, then concrete proposals), each time a row came in. Under those measures sat the
   parts' own setup:
   - `PlatformViewRepresentableAdaptor.makeViewProvider` for the menu button and the web view;
   - `Text.resolve` and `ResolvedStyledText` for the text;
   - `_makeView` of modifiers;
   - `GestureViewModifier`.
2. **One SwiftUI `Menu` per row.** The "…" button resolved its whole menu, date title
   included, for each row. Removing it alone gave 17/26 ms/s in one run. Runs were noisy:
   menu with context menu gave 51/50. The `ShareLink` per row gave 46/38 when removed.
3. **`.sensoryFeedback` per row.** On every question option row, the question card and the
   code card's copy button, as earlier rounds found for the swipe row.
4. **Live inserts above the reader.** `upsert(atTop: true)` put each new event into
   `visibleItems` above the visible rows while the person read below the top. That shifted
   every row and re-laid out the lazy stack (`ForEachState.forEachItem` over all 300
   rows) at 2–5 events a second.

Tried and rejected, with numbers:

- `List` instead of `LazyVStack`: 99.7 ms/s under live load, against 41 for the base.
- A `UICollectionView` with a diffable data source and `UIHostingConfiguration` cells:
  133–141 ms/s. Self-sizing hosting cells measured each row again on every reuse. Both
  experiments were reverted.

## Changes on the branch

These are on the branch. None measurably lowered the hitch time ratio in a same-hour A/B (next section).

| Fix | Where |
| --- | --- |
| One-pass cell layout: `FeedCellLayout` (avatar plus a column of exactly the remaining width) and `FeedColumnLayout` (each part proposed the column width once, `EmptyView` parts take no space) replace the cell's `HStack`/`VStack` | `FeedRowControls.swift`, `FeedCell.swift` |
| The "…" menu is a `UIButton` with `showsMenuAsPrimaryAction` and a `UIDeferredMenuElement`: the menu is built when it opens. The long-press menu reads the same action list (`menuActions`). | `FeedRowControls.swift` |
| Share opens a `UIActivityViewController` on tap instead of a `ShareLink` per row | `FeedRowControls.swift` |
| Per-row `.sensoryFeedback` replaced by UIKit generators fired in the action (selection when a question option's choice changes, impact on submit and on copy) | `CardViews.swift`, `CodeCard.swift` |
| A fling shows each web body as a text placeholder at its cached or estimated height. It renders when the scroll slows below 600 pt/s or stops (`FeedScrollMotion`: fast above 1500 pt/s). Once shown, a web body stays. | `FeedScrollMotion.swift`, `FeedCell.swift`, `FeedScreen.swift` |
| While the person reads below the top (`isReadingBelowTop`), a new event waits behind the "N new" pill, out of `visibleItems` and nothing inserted above them. It is still in `items`, so it is counted for the badge, saved and answerable. Back at the top, or on the pill, it shows. | `FeedStore.swift` |
| `FeedPlainText`'s answer cached per body (`FeedInlineTextCache`); the quote bubble is one `Shape` | `FeedPlainText.swift`, `QuoteBubble.swift` |
| Rig: realistic pressure, per-frame main-thread CPU, churn log opt-in (it reflected over every changed event on the main thread inside the timed window), `sample` mode, a run host apart from the build host | `FeedStress.swift`, `FrameIntervalLog.swift`, `verify/feedperf/*` |

## Before and after

Same simulator (iPhone 16 Plus, iOS 26.5, mini-cmux15), same pressure (320 events, autoscroll down
and up at 2400 pt/s), base and fix builds run back to back in the same hour. Hitch ms/s, main-thread
CPU per second of scrolling, frames whose main thread overran a frame, p99 of main-thread CPU per frame.

| Build | When | Hitch ms/s | Main CPU ms/s | Busy frames | Main CPU p99 per frame |
| --- | --- | --- | --- | --- | --- |
| base | 10-22 21:2x | 49.9 | n/a | 152 | 19.0 ms |
| fix `7cded2f` | 10-22 21:2x | 66.4 | 182.0 | 211 | 20.6 ms |
| base | 10-22 21:4x | 58.1 | 185.7 | 202 | 19.5 ms |
| fix `0be54e8` (review fixes, lazy long-press menu) | 10-22 21:4x | 60.8 | 189.0 | 193 | 20.4 ms |
| fix `7cded2f` with the layout height cache | 10-22 | 64.8–69.4 | 184 | 203–232 | 20.6–21.3 ms |
| fix pre-merge with the layout height cache | 10-22 | 65.4–67.7 | 183 | 104–220 | 20.9–21.4 ms |

**Result: no measurable improvement over base.** Fix and base are within run-to-run noise: about
50–60 ms/s for base and 60–69 for fix. Single runs swing by ±10 ms/s. The target (< 5 ms/s, no frame
over 33 ms) is not met by either build; both have p99 frame time 36–37 ms and max 43–45 ms.

Earlier single runs during the work showed 28 and 24 ms/s (`step2`, `step3-2400`, 10-21 23:41 and
23:59). No base run was made in that window, and later builds of the same code, both pre-merge and with the
same layout cache, never reproduced them. Those numbers reflect the host at that hour, not the code.
The 1 ms `sample` profiles of base, step3 and the pre-merge commit spend the same main-thread time
in the same frames:

- `LazyHVStack.lengthAndSpacing` → the cell layout;
- `_makeView` of row modifiers;
- `Text.resolve` / `ResolvedStyledText`;
- `PlatformViewRepresentableAdaptor.makeViewProvider`.

What the per-frame CPU does show: the hitches are the app's own main-thread work. More than 90 % of
hitched frames had over 12 ms of main-thread CPU in that frame. The work is one burst of 14–20 ms
for each row about 400 pt tall that scrolls in, every 8–11 frames at this speed. A row with only
its avatar, or a plain `Text` row, scrolls with 0 ms/s. The cost is building a full SwiftUI row
(header, quote, chip, body, card, footer, swipe row, menus) the first time it appears. Trimming
individual parts (menus, share, haptics, one-pass layouts) did not reduce that burst on this rig.

What would: not building a full SwiftUI row tree per row as it scrolls in. Options, none built here:

- A UIKit cell layout without per-row `UIHostingConfiguration`. The hosting-cell collection view
  tried here was worse, at 133–141 ms/s.
- Rows sized from a precomputed height model, so the lazy stack never measures a new row.
- Prebuilding rows off screen ahead of the scroll.


## Tests

Swift Testing on mini-cmux11s (`swift test --filter` of the Feed suites): 41 tests in 9
suites passed. They include the new suites written before their fixes, each committed red
first:

- `FeedHoldNewTests`: a held event is not in `visibleItems` but is counted. It joins at the
  top on return or on the pill. Changes to shown events still apply. A withdrawn held event
  leaves the pill. An event seen at the top is never hidden later. Red at `942f5c70c41d`:
  it did not compile, because `isReadingBelowTop` did not exist.
- `FeedScrollMotionTests`: a reading drag versus a fling, hysteresis while slowing, a stop
  that settles, and a jump that is not a fling. Committed at `6b098215f096` before its use.
- `FeedPlainTextTests.inlineTextIsParsedOncePerBody`.
- `FrameIntervalStatsTests.mainThreadCPUIsEncoded`.

The rest of the CmuxMobileKit suites run in CI (`cmux-next-ios kit tests`).

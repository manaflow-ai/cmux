# Feed scrolling: UIKit rows (verification)

Branch `feat-cmux-next-ios-feed-uikit`, 2026-10-22 and 2026-10-23. This branch replaces #24467,
which measured SwiftUI row trimming and found no gain.

## What changed

The Feed's rows used to be a `LazyVStack` of SwiftUI rows. Each row that scrolled in cost 14 to
20 ms of main-thread work: SwiftUI built and measured the full row tree (#24467's 1 ms
`sample` profiles: `LazyHVStack.lengthAndSpacing`, `_makeView`, `Text.resolve`). The Feed is
now:

- `FeedCollection.swift`: a `UICollectionView` with a diffable data source keyed by event id
  (`FeedListController`). Live inserts and removals are snapshot edits (`FeedSnapshotEdit`).
  The row under the reader stays where it is, and new rows above it count into the "N new"
  pill. A store update re-keys only the rows it changed.
- `FeedListLayout.swift`: a one-column layout whose frames are prefix sums of known heights,
  with visible rows found by binary search.
- `FeedRowLayout.swift`: everything a row draws (frames and attributed text) for one
  `FeedRowKey` (the event, the row's state, the width and the text size). It is computed off
  the main thread and kept until the key changes. The read flag and the time are drawn, not
  laid out.
- `FeedRowCell.swift`: UIKit views only, with no SwiftUI hosting in rows. The subviews are reused, and the
  parts a row may not show are made on first use. Labels draw asynchronously.
- `CmuxMobileMarkdown/NativeMarkdown.swift`: markdown as native attributed text, code cards
  and tables, matching the web renderer's metrics (`markdown.css`). Only bodies with math
  still use the pooled web view, once scrolling settles.

Every interaction stays:

- the reply box;
- question cards, with saved drafts;
- Allow and Deny, with Face ID through `store.respond`;
- Answer in Terminal, and Decline;
- the "…" and long-press menus;
- the rounded swipe actions (`RowSwipeActionStyle`), including the RowSwipeActions drawer handoff;
- quote bubbles;
- Show more, Copy and Share;
- pull to refresh;
- routing to the source Mac (`FeedRouting`);
- the demo driver commands.

## Measurements

The rig (`verify/feedperf/`) records frame intervals and main-thread CPU per frame from the
app's own frame log (`CMUX_MOBILE_FRAMELOG=1`). The simulator displays at 60 Hz, so a frame
is 16.67 ms. Base: origin/feat-cmux-next `2ad7671e9166` with the same rig.

### Synthetic pressure

On an iPhone 16 Plus simulator (iOS 26.5, mini-cmux15), runs alternate base, fix, base, fix
within the same hour. The load is 320 events of 8 kinds (permission cards with long commands,
questions, failed and finished cards, markdown with code and tables, quotes, two Macs,
replies). The list scrolls to the bottom and back at 2400 pt/s, without live traffic and with
4 live changes a second. Values are hitch ms/s, max frame time, and main-thread CPU ms/s.

| Run | Base | Fix |
| --- | --- | --- |
| no live, 1 | 49.6 ms/s, max 62.0 ms, 183 | **1.0 ms/s, max 35.8 ms, 59** |
| no live, 2 | 38.4 ms/s, max 43.6 ms, 179 | **0.7 ms/s, max 33.3 ms, 59** |
| live 4/s, 1 | 48.8 ms/s, max 47.3 ms, 193 | **3.3 ms/s, max 51.3 ms, 82** |
| live 4/s, 2 | 50.5 ms/s, max 59.2 ms, 187 | **2.2 ms/s, max 41.0 ms, 79** |
| no live, head `3687fdf` | | **0.2 ms/s, max 33.3 ms, 59** |
| live 4/s, head `3687fdf` | | **1.7 ms/s, max 36.5 ms, 78**, 0 busy frames |

An earlier same-hour set (`final`, 2 reps) gave 54.5 to 62.0 ms/s for base and 1.1 to 2.3
ms/s for fix. In every run, p99 frame time is 35 to 37 ms for base and 16.67 ms for fix.

The target was under 5 ms/s and no frame over 33 ms.

- Hitch time: met in every fix run.
- Frame time: p99 is 16.67 ms, but each run still has 0 to 5 single frames of 34 to 51 ms.
  Without live traffic, the most recent runs had none over 33.3 ms.
- Most of those frames are a cell made for the first time mid-scroll (its first CoreAnimation
  commit) or a live insert landing in that frame.

### Real use

Two rig Macs (`verify/multimac/rig.py`, real cmux-next builds signed in to the dev account) feed
one phone simulator (iPhone 17 Pro, `cmux-feedperf`, mini-cmux8s) over the real link.

- On mini-cmux15, a real Codex session and a real Claude session (acpmux harnesses `codex` and
  `claude-sr2`) work through prompts that read files, run commands and answer with code and
  tables (`live_feed_agents.sh`).
- On mini-cmux8s, the fake agent asks a permission every 6 s.

The phone links both Macs, waits, then scrolls its real Feed with the same autoscroll
(`live_feed.py`). mini-cmux8s was shared with other jobs (load average 100 to 260), so
these frame times include host noise. Late frames whose main thread was busy (over 12 ms of
main-thread CPU in that frame) are the app's own.

The final pair ran on mini-cmux15, which is quiet: load average under 25, the phone simulator
there, both rigs linked. Base and new ran back to back on the same real Feed, which held
hundreds of events after an hour of agent work. Each pass scrolls the whole Feed. Columns:
hitch ms/s, max frame, main-thread CPU ms/s.

| Pass | Base `2ad7671` | New `3687fdf` |
| --- | --- | --- |
| down, first after launch (75 s) | 419.8, 232.6 ms, 575 | 195.1, 157.1 ms, 291 |
| up (145 s) | 34.8, 44.6 ms, 180 | **0.0, 16.7 ms, 59** |
| down (145 s) | 23.4, 42.8 ms, 178 | **0.1, 33.3 ms, 52** |
| up (145 s) | 25.0, 276.6 ms, 178 | **0.0, 16.7 ms, 52** |

Once the Feed has loaded, scrolling the real Feed has no hitches: 0.0 to 0.1 ms/s and one late
frame in 435 s, with agents still posting.

All of the new build's late frames fall in the first 20 s after launch. In that time the main
thread is busy 765 to 944 ms/s. A 22 s `sample` from launch puts it in the live link's
first sync: `LiveCoordinator.finishServing` → `AcpmuxHub.bind/seedPending`,
`LiveFeed.handle/hydrate`, `WorkspaceSync.refresh` and `FeedStore.upsert/mergeHistory`, as
hundreds of events arrive at once. Base has the same startup cost, and it is not the Feed
list's. Spreading that sync out is a separate change (CmuxMobileLive).

## Tests

`swift test --filter "Feed|TerminalFeed|MultiMac|FrameInterval"` on mini-cmux7s: 69 tests in
19 suites passed. New since the base:

- `FeedListPlanTests`, committed red first at `8ef597f55f73`:
  - a row is laid out once per event, state, width and text size;
  - other rows keep their layout;
  - gone rows are pruned;
  - a changed event reconfigures only its row;
  - the same events again change nothing;
  - inserts above the reader are counted;
  - snapshot edits: a live insert, a removal, and a re-sort, which rebuilds;
  - only events never seen before count as new.

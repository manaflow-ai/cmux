# Startup performance

The startup benchmark compares two exact cmux-tui commits. It uses product output and public socket commands as readiness events. It does not use sleeps, file-existence or socket-path polling for synchronization, quiet periods, or retry polling.

## Scenarios

- Cold starts a new interactive process with fresh isolated state. The event ends after the raw PTY stream contains its unique session label and a later frame-end cursor visibility or cursor position command.
- Warm starts an attach client after a headless daemon has printed its readiness line and answered session current ping. The event ends at the attach client's first complete frame.
- Headless starts a new daemon. The event ends after the readiness line and a successful session current ping.
- Restored creates a real terminal through the public CLI, stops the daemon, and restarts it with the same state. The event ends after the readiness line and a terminal list response that contains the saved terminal ID.
- Incompatible changes a valid registry schema to an unsupported value. The event ends at nonzero process exit and requires exact equality for the normalized primary public diagnostic for that binary and session. The benchmark also proves that startup did not change the stored schema.

Each cold and headless launch uses a fresh process, configuration root, and state root. The workflow does not clear the operating system page cache.

## Method

AppContainer feasibility schema 4 uses the documented unpackaged launch path. The trusted account-owned broker disables all privileges, enables only `SeChangeNotifyPrivilege`, and proves that exact one-privilege set with a non-AppContainer token, zero restricting SIDs, and the exact account authentication ID. It then calls `CreateProcessW` with `STARTUPINFOEX`, `SECURITY_CAPABILITIES`, no capabilities, and the exact three-handle list. The suspended output token must have the exact AppContainer SID, zero restricting SIDs, zero capabilities, low integrity, the same account authentication ID, and only `SeChangeNotifyPrivilege` enabled. The in-product proof requires the same privilege set. This privilege permits path traversal but does not grant file read, write, or directory-list access.

The hosted workflow builds the candidate product in a separate job and runner. That untrusted job uploads one closed artifact with the candidate binary, available symbol files, and a manifest of all paths, sizes, and SHA-256 hashes. The clean benchmark job rejects symlinks, unsafe paths, extra files, missing files, identity mismatches, size mismatches, and hash mismatches before it imports the candidate product. It then builds the baseline product from the measured baseline checkout and all benchmark infrastructure from the trusted default-branch checkout. Candidate build scripts never run in the benchmark job.

The workflow has no automatic pull request trigger. An authorized maintainer starts each comparison from the exact baseline revision and selects the exact candidate SHA. The trusted SHA is the workflow revision and owns the Zig parser, Rust setup action, benchmark harness, supervisor, preflight, harness tests, evidence verifier, and every native-profile harness. The baseline SHA must be identical to that trusted SHA. The candidate must descend from the trusted baseline. The candidate checkout in the benchmark job supplies read-only source, toolchain, and Ghostty identity data. Only the imported candidate product binary runs there.

Manual runs start from the branch or revision that contains the trusted benchmark runner. `GITHUB_SHA` is both the trusted infrastructure SHA and the measured baseline SHA. The candidate is a full lowercase 40-character commit SHA:

```bash
gh workflow run cmux-tui-startup-benchmark.yml --repo manaflow-ai/cmux --ref <trusted-baseline-ref> \
  -f candidate_sha=<40-character-sha>
```

Each scenario has exactly 10 warmup pairs and 50 measured pairs. The workflow has no count inputs. One harness on one runner launches each pair serially. Even pairs run the baseline first. Odd pairs run the candidate first. A failure to observe an event stops the job. Timing differences do not fail the job because shared hosted computers have variable load.

The JSON artifact contains samples in run order and sorted order. It reports minimum, mean, population standard deviation, median absolute deviation, p50, p90, p95, p99, and maximum. Paired deltas use candidate minus baseline. Negative deltas mean that the candidate was faster. Interactive evidence records one-shot response counts for each recognized terminal query. Windows requires one cursor-position reply and at least one other recognized reply per launch. macOS and Linux require at least four recognized replies per launch.

The artifact records the trusted, baseline, and candidate SHAs, plus exact Ghostty, binary, required Zig, and Rust toolchain identities. Every source identity is a lowercase 40-character SHA. The workflow lists the trusted harness test names, requires a nonzero count, records that count, and then runs the same target. The candidate artifact validator recomputes every imported file size and hash. The workflow hashes the harness, supervisor, verifier, product binaries, manifests, source identities, and evidence files again after all product execution. The harness also rechecks both product binaries, both source trees, both Ghostty trees, the trusted source, supervisor, and sandbox preflight before it writes the report. The candidate must expose the exact cmux and Ghostty commits in its public version. A baseline without that version stamp remains measurable through the post-build hash, while any baseline stamp that is present must match. The artifact also records the runner image, CPU, physical and logical core counts, memory, kernel, Rust, and Cargo versions. The profile evidence includes both measured binaries, available target symbol files, and a manifest with their SHA-256 hashes and sizes. The final closed artifact manifest lists every other evidence file with its path, size, and SHA-256 hash. The verifier rejects missing files, extra files, symlinks, hash drift, incomplete raw distributions, zero harness tests, and missing required profile output immediately before upload.

Every baseline and candidate execution uses the trusted supervisor, including version checks, fixture setup, public RPC commands, measured launches, cleanup, and profiles. The supervisor sends a nonce-bound READY event, waits for ARM, and records the platform monotonic start time immediately before product creation. On Windows, it keeps the public control channel open until it relays a bounded ProductStarted record. This record proves `CreateProcessAsUserW` success, product token limits, exact Job membership, a prior resume count of one, and the product process and primary-thread IDs before the broker waits for product exit. The outer supervisor duplicates the broker's product process and thread handles, verifies that they match those IDs, and sends a nonce-bound adoption acknowledgement before the broker may close its copies. These handles stay out of the product handle list. A separate 50-second post-ARM deadline leaves time for the broker's 30-second product-status deadline and 10-second cleanup. The controller races complete or partial product output, the native exit record, and the public failure record on one event stream. If a later product event fails, it preserves an 8 KiB raw stdout tail and the product lifecycle beside the requested preflight output before it terminates the supervisor. On other platforms, a peer that already closed its socket produces `NotConnected`, which the local drop owner accepts as closed. All other shutdown errors remain fatal. The product cannot reopen the removed control and timing paths. Linux uses Bubblewrap namespaces with only the fixture root writable. It records the Bubblewrap version, both hosted user-namespace settings, `NoNewPrivs=1`, and zero effective capabilities. If the host blocks unprivileged user namespaces, the trusted workflow runs Bubblewrap through sudo under a dedicated UID and GID and drops all capabilities. macOS gives Seatbelt the exact per-launch fixture root under a deterministic low-privilege account. A workflow-owned group supplies fixture access, but Seatbelt is the write boundary. Both the supervisor and harness register process-exit events, kill all processes for that launch account, wait to a hard deadline, require the account process list to be empty, and delete the account. Windows logs on a unique local account and starts the trusted bootstrap with that account's normal primary token in a non-breakaway Job Object. For each launch, the supervisor creates one nonce-bound noninteractive window station and desktop. Creation-time security descriptors grant the trusted supervisor full ownership and grant the exact account and restricting SID only the documented noninteractive connection rights. A low-integrity mandatory label prevents writes across the integrity boundary. The bootstrap and product use the explicit private desktop name. Neither process inherits a desktop or window-station handle. The supervisor retains both objects until the Job reports ACTIVE_PROCESS_ZERO, then closes the desktop before the station. The preflight alone loads the account profile. It proves that write access to the existing `HKEY_CURRENT_USER\\Software` key returns `ACCESS_DENIED`. The standalone bootstrap owns a non-inheritable query-only handle for the exact private Job. It proves its own membership, creates a write-restricted, low-integrity version of its own primary token with the exact unique restricting SID, and uses `CreateProcessAsUserW` to create the product. Before resume, it proves that the product has the broker authentication ID, the exact restricting SID, low integrity, no enabled privilege, and membership in the exact private Job. The product receives only the explicit stdin, stdout, and stderr handle list. The preflight also proves that breakaway fails and the Job reports `ACTIVE_PROCESS_ZERO`. Each preflight unloads its profile view. The workflow deletes the exact account profile only after it proves that all account processes and loaded profile views are gone. Every platform also proves that the product cannot connect to a trusted listener and that a trusted controller cannot connect to a product listener. A platform preflight proves that fixture writes work, adjacent writes fail for the product and a detached child, the READY/ARM timing record is unique, and no descendant survives. There is no direct-launch fallback.

Windows runs this AppContainer feasibility gate outside product timing. The controller creates separate nonce-owned staging and writable fixture directories with final creation-time security descriptors. Runner, Administrators, and SYSTEM have full access. The benchmark account and AppContainer SID have read and execute access to staging and full access to the fixture. The controller creates the staged probe with a direct file-specific read-and-execute DACL and low-integrity label, then rehashes it before broker launch. The account broker disables all token privileges, enables only `SeChangeNotifyPrivilege`, and retains that live token handle before it validates the staged path. Product launch uses the same handle for the recorded pre-launch token proof. The broker and AppContainer product must both fail to create a staging file or open the staged probe for write. No checkout, runner temporary parent, or other pre-existing ACL is changed. The controller snapshots the existing fixture-parent descriptor, compares its hash after the run, and requires it to be byte-identical. Job `ACTIVE_PROCESS_ZERO` precedes deletion of both owned directories. Schema 4 records both creation ACLs, the launch API, exact privilege proofs, staged-probe hash, write denials, owned-directory deletion, and unchanged parent descriptor. The broker has no config, success, or failure file transport. The trusted controller writes one bounded canonical config record to a dedicated stdin pipe. Broker stdout returns exactly one canonical tagged success or failure record. Both sides reject extra bytes, unknown fields, noncanonical JSON, or a wrong nonce. Failure stages are `config-receive`, `config-validate`, `product-launch`, `success-evidence-encode`, and `success-evidence-write`. The trusted controller writes the external failure artifact. A separate bounded stderr pipe preserves the primary error.

The Windows product creator is a small native C bootstrap built with MSVC. The bootstrap uses the Windows subsystem and the supervisor starts it with `CREATE_NO_WINDOW`, so Windows does not create a console for this broker. Its custom Win32 entry point has no C runtime startup, allocator, or string call before the fixed protocol is consumed. The entry point initializes the MSVC security cookie before it calls stack-protected code. The `/NODEFAULTLIB` link names `libcmt.lib` and `libvcruntime.lib` explicitly so the linker can extract the static MSVC compiler-support members for the security cookie, GS checks and unwind handler, and stack probing. The custom entry point does not reference or run a CRT startup member, and the bootstrap does not reference a UCRT API. Control Flow Guard uses the compiler and linker `/guard:cf` options with `/DYNAMICBASE`; it needs no separate runtime library. The bootstrap has no Rust runtime and no cmux, Ghostty, SQLite, terminal, rendering, or configuration dependency. Rust owns the encoder and decoder for its fixed, versioned, bounded binary protocol. The native parser independently checks the same schema, record bounds, nonce, paths, handles, hashes, and restricting SID. The outer supervisor hashes the bootstrap before launch, starts it under the normal benchmark account token, and assigns it to the Job before resume. Resume must report one prior suspension. The 30-second cold-loader deadline starts only after that exact return. The supervisor supplies the entry-checkpoint path and nonce through two dedicated environment records. The custom entry reads and clears them, writes the nonce-bound entry checkpoint, and then parses the command line. It requires both parsed values to match the entry identity. Checkpoint absence therefore means that the custom entry did not run. Later checkpoint stages record config-read start and config consumption before any pipe event can hide those boundaries. The bootstrap consumes its config, proves that it cannot write beside its trusted binary, validates the transferred handles, and proves exact Job membership. It enables `SeIncreaseQuotaPrivilege` only in the trusted broker, creates the restricted-self product token with `DISABLE_MAX_PRIVILEGE | WRITE_RESTRICTED`, and records product t0 immediately before `CreateProcessAsUserW`. The product cannot inherit the privilege or the removed entry records. After the exact product proofs and resume, the broker sends ProductStarted before it waits for exit. The Job owner rehashes the bootstrap after the Job is empty. The workflow grants only `SeIncreaseQuotaPrivilege` to the exact generated account SID before `LogonUserW`, and removes that LSA account right before it deletes the account. It also gives the account read and execute access to the bootstrap and traversal access to its trusted parents, but no write access. Bootstrap evidence schema 5 records the bootstrap hash, config nonce and consumption, prior bootstrap and product suspend counts, READY elapsed time, broker, restricted-token, and product authentication IDs, exact restricting SID, privilege presence and enablement, `CreateProcessAsUserW` success, token restriction and integrity proofs, exact product Job proof, product process and primary-thread IDs, trusted-probe write denial, bootstrap self-write denial, and the private desktop creation, assignment, and post-Job close proofs. Preflight evidence schema 8 copies and validates these fields.

If the Windows bootstrap does not reach READY within its 30-second loader deadline, or if a started product does not report status within 30 seconds, the same hashed trusted supervisor starts once as a fail-only diagnostic helper outside the private Job. The outer supervisor duplicates the blocked process and primary-thread handles into the suspended helper and verifies their IDs, writes a random-nonce-bound config, and then resumes the helper. The helper has no `CMUX_BENCH_*` environment values. The target bootstrap environment contains only its two nonsecret entry-identity values from that namespace. The helper records the suspended primary-thread RIP and RSP, a bounded instruction window, Wait Chain Traversal results, and a minimal thread-info minidump. The bounded module map is best-effort because Windows can reject module enumeration while the loader is incomplete. A virtual-memory query and mapped-file lookup resolve the instruction owner when possible, and the report records the Windows error when either owner path fails. The report and dump are regular files under the exact fixture root, have nonce-bound names, hashes, and size caps, and are copied beside preflight evidence. A five-second parent deadline kills and reaps a stuck diagnostic helper. The existing Job owner then terminates the measured tree and requires `ACTIVE_PROCESS_ZERO`. The success path and product t0 are unchanged. On macOS, the supervisor canonicalizes the existing per-launch fixture root before account access and passes the same kernel-visible path to Seatbelt.

Run the workflow from GitHub for comparable evidence. The workflow uploads JSON, Markdown, metadata, diagnostics, exact attribution binaries, target symbol files, required native profiles, and the closed artifact manifest.

Each measured process reaches its observable event, validation, exit, reap, and any owned reader-thread join before its fixture root can enter the deferred-reclamation ledger. Captured commands drain stdout and stderr into fixed-size in-memory tails. Their owned readers have bounded cancellation, so inherited pipe writers cannot block completion and noisy failures cannot fill the runner disk. Headless and PTY failures stop the complete launched process tree and use bounded process and reader completion before joining. Windows explicitly cancels owned synchronous pipe and ConPTY reads after process exit. A PTY failure records the bounded output tail plus observed query and written-response counts before cleanup. Failed samples never authorize root deferral. No fixture deletion runs during timed work. Pair checkpoints are diagnostics only and cannot resume a report on another runner. A complete report still requires all 10 warmups and all 50 measured pairs for every scenario. The report and lifecycle evidence are flushed before hosted cleanup can delete deferred roots.

Unix hosted jobs use a short run-specific fixture parent under `/tmp` so AF_UNIX control paths stay within the platform socket limit. Windows uses a short validated child of the runner temporary directory. Both targets use equal-length roots inside the same parent.

## Native profiles

The example has a one-sample profile mode. A launcher prefix wraps the trusted supervisor outside the sandbox and still passes PTY input and output. The supervisor records the product start inside the sandbox, so profiler setup is outside the measured interval. Linux requires a nonempty strace summary and adjacent profile report for each target. macOS requires a nonempty xctrace Time Profiler trace and adjacent profile report for each target. Filter that trace to the exact cmux-tui process and binary in the report. Windows requires a nonempty WPR ETL trace and adjacent profile report for each target. The final artifact closure gate fails if a required profile is absent. macOS Allocations and file activity plus Linux raw strace, massif, and perf remain supplemental and keep diagnostic output when unavailable.

Profile mode still validates the selected source SHA, Ghostty SHA, binary hash, and scenario event. It writes `startup-profile-<target>-<scenario>.json`.

# Startup performance

The startup benchmark compares two exact cmux-tui commits. It uses product output and public socket commands as readiness events. It does not use sleeps, file-existence or socket-path polling for synchronization, quiet periods, or retry polling.

## Scenarios

- Cold starts a new interactive process with fresh isolated state. The event ends after the raw PTY stream contains its unique session label and a later frame-end cursor visibility or cursor position command.
- Warm starts an attach client after a headless daemon has printed its readiness line and answered session current ping. The event ends at the attach client's first complete frame.
- Headless starts a new daemon. The event ends after the readiness line and a successful session current ping.
- Restored creates a real terminal through the public CLI, stops the daemon, and restarts it with the same state. The event ends after the readiness line and a terminal list response that contains the saved terminal ID.
- Incompatible changes a valid registry schema to an unsupported value. The event ends at nonzero process exit and requires exact equality for the normalized primary public diagnostic for that binary and session. The benchmark also proves that startup did not change the stored schema.

Each cold and headless launch uses a fresh process, configuration root, and state root. The workflow does not clear the operating system page cache.

## Method

The hosted workflow builds the candidate product in a separate job and runner. That untrusted job uploads one closed artifact with the candidate binary, available symbol files, and a manifest of all paths, sizes, and SHA-256 hashes. The clean benchmark job rejects symlinks, unsafe paths, extra files, missing files, identity mismatches, size mismatches, and hash mismatches before it imports the candidate product. It then builds the baseline product from the measured baseline checkout and all benchmark infrastructure from the trusted default-branch checkout. Candidate build scripts never run in the benchmark job.

The workflow has no automatic pull request trigger. An authorized maintainer must start each comparison and explicitly select the exact baseline and candidate SHAs. Three identities remain separate. The trusted SHA is the default-branch workflow revision and owns the Zig parser, Rust setup action, benchmark harness, supervisor, preflight, harness tests, evidence verifier, and every native-profile harness. The baseline SHA is the measured older product and must be an ancestor of the trusted SHA. The candidate checkout in the benchmark job supplies read-only source, toolchain, and Ghostty identity data. Only the imported candidate product binary runs there.

Manual runs must start from the repository default branch. `GITHUB_SHA` is the trusted infrastructure SHA. Both measured revisions must be full 40-character commit SHAs:

```bash
gh workflow run cmux-tui-startup-benchmark.yml --repo manaflow-ai/cmux --ref main \
  -f baseline_sha=<40-character-sha> -f candidate_sha=<40-character-sha>
```

Each scenario has 10 warmup pairs and 50 measured pairs. Even pairs run the baseline first. Odd pairs run the candidate first. A failure to observe an event stops the job. Timing differences do not fail the job because shared hosted computers have variable load.

The JSON artifact contains samples in run order and sorted order. It reports minimum, mean, population standard deviation, median absolute deviation, p50, p90, p95, p99, and maximum. Paired deltas use candidate minus baseline. Negative deltas mean that the candidate was faster. Interactive evidence records one-shot response counts for each recognized terminal query. Windows requires one cursor-position reply and at least one other recognized reply per launch. macOS and Linux require at least four recognized replies per launch.

The artifact records the trusted, baseline, and candidate SHAs, plus exact Ghostty, binary, required Zig, and Rust toolchain identities. The candidate artifact validator recomputes every imported file size and hash. The workflow hashes the harness, supervisor, verifier, product binaries, manifests, source identities, and evidence files again after all product execution. The harness also rechecks both product binaries, both source trees, both Ghostty trees, the trusted source, supervisor, and sandbox preflight before it writes the report. The candidate must expose the exact cmux and Ghostty commits in its public version. A legacy baseline without that version stamp remains measurable through the post-build hash, while any baseline stamp that is present must match. The artifact also records the runner image, CPU, physical and logical core counts, memory, kernel, Rust, and Cargo versions. The profile evidence includes both measured binaries, available target symbol files, and a manifest with their SHA-256 hashes and sizes.

Every baseline and candidate execution uses the trusted supervisor, including version checks, fixture setup, public RPC commands, measured launches, cleanup, and profiles. The supervisor sends a nonce-bound READY event, waits for ARM, and records the platform monotonic start time immediately before product creation. On Windows, it keeps the public control channel open until it relays a bounded ProductStarted record. This record proves `CreateProcessAsUserW` success, product token limits, exact Job membership, and a prior resume count of one before the broker waits for product exit. A separate 50-second post-ARM deadline leaves time for the broker's 30-second product-status deadline and 10-second cleanup. The preflight keeps the relayed record in trusted memory. If a later product event fails, it writes the record beside the requested preflight output after the measurement is invalid, before it terminates the supervisor. On other platforms, a peer that already closed its socket produces `NotConnected`, which the local drop owner accepts as closed. All other shutdown errors remain fatal. The product cannot reopen the removed control and timing paths. Linux uses Bubblewrap namespaces with only the fixture root writable. It records the Bubblewrap version, both hosted user-namespace settings, `NoNewPrivs=1`, and zero effective capabilities. If the host blocks unprivileged user namespaces, the trusted workflow runs Bubblewrap through sudo under a dedicated UID and GID and drops all capabilities. macOS gives Seatbelt the exact per-launch fixture root under a deterministic low-privilege account. A workflow-owned group supplies fixture access, but Seatbelt is the write boundary. Both the supervisor and harness register process-exit events, kill all processes for that launch account, wait to a hard deadline, require the account process list to be empty, and delete the account. Windows logs on a unique local account and starts a small trusted account launcher with that account's normal primary token in a non-breakaway Job Object. The launcher creates the trusted bootstrap suspended on the operating system-selected noninteractive window station and desktop, then transfers its process and primary-thread handles to the supervisor for validation before the bootstrap resumes. The preflight alone loads the account profile. It proves that write access to the existing `HKEY_CURRENT_USER\\Software` key returns `ACCESS_DENIED`. The standalone bootstrap owns a non-inheritable query-only handle for the exact private Job. It proves its own membership, creates a write-restricted, low-integrity version of its own primary token with the exact unique restricting SID, and uses `CreateProcessAsUserW` to create the product. Before resume, it proves that the product has the broker authentication ID, the exact restricting SID, low integrity, no enabled privilege, and membership in the exact private Job. The product receives only the explicit stdin, stdout, and stderr handle list. The preflight also proves that breakaway fails and the Job reports `ACTIVE_PROCESS_ZERO`. Each preflight unloads its profile view. The workflow deletes the exact account profile only after it proves that all account processes and loaded profile views are gone. Every platform also proves that the product cannot connect to a trusted listener and that a trusted controller cannot connect to a product listener. A platform preflight proves that fixture writes work, adjacent writes fail for the product and a detached child, the READY/ARM timing record is unique, and no descendant survives. There is no direct-launch fallback.

The Windows product route uses two small native C programs built with MSVC. The supervisor starts a USER32-free account launcher with `CreateProcessWithTokenW`, `CREATE_NO_WINDOW`, and the inherited runner desktop. The launcher enables its existing `SeIncreaseQuotaPrivilege`. It starts the product bootstrap with `CreateProcessAsUserW`, `CREATE_NO_WINDOW`, and an empty desktop name. Windows selects the unique account logon session's noninteractive station before the USER32-using bootstrap starts. Both custom entry points use bounded fixed protocols and no cmux product code. The workflow audits both import tables. It rejects USER32, GDI32, and Win32u imports from the account launcher.

The launcher passes only the fixed bootstrap handle list. It also receives one non-inheritable `PROCESS_DUP_HANDLE` target for the supervisor. While the bootstrap is suspended, the launcher duplicates the bootstrap process and primary-thread handles into the supervisor and sends their values with the nonce, exact PIDs, hashes, Job proof, privilege proof, session proof, and stage markers. The supervisor adopts the handles only after it proves their types, image path and hash, private Job membership, account SID, authentication ID, logon SID, session ID, and suspend count. A nonce-bound acknowledgment is required before resume. Exit waits, hang capture, and cleanup use the adopted bootstrap handles. Extra or late adoption records fail and close their handles. The bootstrap then reads the OS-assigned object names, rejects `WinSta0`, requires the default desktop, and applies exact logon-SID DACLs and low-integrity labels. It creates the restricted product on the observed qualified desktop and proves the product token, session, desktop, label, and Job identities before resume. Bootstrap evidence schema 8 and preflight evidence schema 11 record the order. Cleanup waits for an empty Job, unloads the profile, removes `SeIncreaseQuotaPrivilege`, proves the right is absent, and deletes the account.

If the Windows bootstrap does not reach READY within its 30-second loader deadline, the same hashed trusted supervisor starts one fail-only diagnostic helper outside the private Job. The supervisor duplicates the adopted bootstrap process and primary-thread handles into the suspended helper. The helper records the suspended primary-thread state, a bounded instruction window, Wait Chain Traversal results, and a minimal thread-info minidump. The bounded module map is best-effort because Windows can reject module enumeration while the loader is incomplete. The report and dump use nonce-bound names, hashes, and size caps under the exact fixture root. A five-second parent deadline kills and reaps a stuck helper. The Job owner then terminates the measured tree and requires `ACTIVE_PROCESS_ZERO`. The success path and product t0 do not change.

Run the workflow from GitHub for comparable evidence. The workflow uploads JSON, Markdown, metadata, diagnostics, exact attribution binaries, available target symbol files, and available native profiles.

Each measured process reaches its observable event, validation, exit, reap, and any owned reader-thread join before its fixture root can enter the deferred-reclamation ledger. Captured commands drain stdout and stderr into fixed-size in-memory tails. Their owned readers have bounded cancellation, so inherited pipe writers cannot block completion and noisy failures cannot fill the runner disk. Headless and PTY failures stop the complete launched process tree and use bounded process and reader completion before joining. Windows explicitly cancels owned synchronous pipe and ConPTY reads after process exit. A PTY failure records the bounded output tail plus observed query and written-response counts before cleanup. Failed samples never authorize root deferral. No fixture deletion runs during timed work. Pair checkpoints are diagnostics only and cannot resume a report on another runner. A complete report still requires all 10 warmups and all 50 measured pairs for every scenario. The report and lifecycle evidence are flushed before hosted cleanup can delete deferred roots.

Unix hosted jobs use a short run-specific fixture parent under `/tmp` so AF_UNIX control paths stay within the platform socket limit. Windows uses a short validated child of the runner temporary directory. Both targets use equal-length roots inside the same parent.

## Native profiles

The example has a one-sample profile mode. A launcher prefix wraps the trusted supervisor outside the sandbox and still passes PTY input and output. The supervisor records the product start inside the sandbox, so profiler setup is outside the measured interval. Linux uses this mode with strace. macOS records all processes with xctrace while the harness keeps direct PTY ownership. Filter that trace to the exact cmux-tui process and binary recorded in the adjacent profile report. Windows records the event harness inside a system-wide WPR capture. All native profile attempts are non-gating. They record permission or tool diagnostics when a profile is unavailable.

Profile mode still validates the selected source SHA, Ghostty SHA, binary hash, and scenario event. It writes `startup-profile-<target>-<scenario>.json`.

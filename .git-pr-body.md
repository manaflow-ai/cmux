## What moved twice

The iPhone composer's `/` list (`ChatComposer.slashSuggestions`) capped its height with `SlashSuggestionsBound(ceiling:, bottom:)`, where `bottom` came from an `onGeometryChange` on **the list itself**. On the list's first frame that value was not known yet, so:

1. the list slid in at the fallback cap (5.5 rows, 242 pt),
2. one layout later its own bottom arrived, the cap became the real room between the header and the card,
3. the list resized again: shrinking with the keyboard up and many commands, growing when there was more room — the "secondary animation that recalculates to shrink stuff".

The code has been there since #27767 (2026-10-30), so it is in every nightly Leo has.

## The design now

The bound is taken from the composer card's top, which is laid out before the list exists and which the list never moves (the stack is bottom-aligned): `SlashSuggestionsBound(ceiling:, cardTop:, gap:)`. The list's first frame already has its final height, so it opens once at one size and only its entrance plays. The keyboard moving the card still re-bounds it, as before.

- `ChatComposer.swift`: `cardTop` measured on `card`; the list's own geometry reader is gone.
- `SlashSuggestionsBound.swift`: `init(ceiling:cardTop:gap:)`.
- `SlashSuggestionsBoundTests.swift`: `theCardTopGivesTheRoomBeforeTheListIsLaidOut`.

## ELI5

When you type `/` on iPhone, a list of commands pops up above the text box. To decide how tall it may be, the list used to measure where its own bottom edge was. It can't know that before it has been drawn once, so its first frame used a guessed height and the next frame snapped it to the real one: the second little resize Leo saw. Now the list asks the text box where its top is instead. The box is already on screen before the list appears, so the list knows its right height from the very first frame and opens once. Nothing else changes: same cap, same gap, and the keyboard still re-bounds it.

## The class and the meta-problem

The class: a view that sizes itself from a measurement of its own frame draws at a guess, then again at the truth. The Mac web `/` menu has a cousin of it (`ui/popupHost.ts` measures the in-page list one frame after it opens and only then may escape to the host's native panel); that path is not touched here and is the next case to look at.

Meta-problem: nothing flags a geometry reader whose value feeds the same view's size. A detector (a lint on `onGeometryChange` writing state read by that view's own `frame`/`Layout`) is a follow-up, not in this PR (new guards need Leo's say-so).
